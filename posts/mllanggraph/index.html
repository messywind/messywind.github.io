LangGraph 学习笔记：Agent、状态图、中间件、记忆与面试要点

1. LangGraph 解决的核心问题

普通的大模型调用通常是一次性的：输入消息，模型生成答案。Agent 系统则需要在一次任务中反复进行判断、调用工具、读取结果、更新状态，并在合适的时候结束。

LangGraph 可以理解为一个面向 Agent 的有状态工作流运行时。它把 Agent 的执行过程表示成图：

  • 状态（State）：流程运行过程中持续传递和更新的数据；
  • 节点（Node）：执行模型调用、工具调用或业务逻辑；
  • 边（Edge）：规定节点之间的流转关系；
  • 条件边（Conditional Edge）：根据当前状态动态选择下一步；
  • 检查点（Checkpoint）：保存某个线程的运行状态，使流程可以继续、恢复或接受人工干预；
  • 存储（Store）：保存能够跨线程、跨会话复用的长期信息。

它的价值不只是“把 LLM 接上工具”，而是让模型能力进入一个可控制、可扩展、可持久化、可观测的工程流程。

2. 四份 Notebook 的学习主线

四个主题可以看成从核心执行到外围能力逐层扩展：

流程内核 StateGraph 显式控制节点、分支、循环和结束条件
横切能力 Middleware 在不改动核心流程的情况下加入预算、安全、上下文治理等能力
状态持久化 Memory 让信息在多轮调用、程序重启或不同会话之间延续

3. 快速入门：先理解 Agent 的运行闭环

3.1 create_agent 是高层抽象

create_agent 适合快速构建常见的工具调用型 Agent。开发者主要提供：

  • 模型；
  • 系统提示词；
  • 可调用工具；
  • 可选的中间件、上下文结构、记忆组件和输出格式。

框架负责组织模型与工具之间的循环。典型过程如下：

flowchart LR
    U["用户消息"] --> M["模型判断"]
    M -->|"无需工具"| A["最终回答"]
    M -->|"生成工具调用"| T["执行工具"]
    T --> O["工具结果写入消息状态"]
    O --> M

这类循环体现了 ReAct 的基本思想：模型根据当前信息决定行动，外部环境返回观察结果，模型再继续判断，直到完成任务。

3.2 工具调用的本质

工具是模型连接外部世界的受控接口，可以对应天气服务、数据库、搜索引擎、计算函数或企业内部 API。

模型并不直接执行函数，而是根据工具的名称、描述和参数结构生成一条调用请求；真正的执行由 Agent 运行时完成。工具结果随后作为新消息进入状态，供模型继续推理。

因此，工具的质量主要取决于：

  • 职责是否单一：一个工具最好只完成一种清晰任务；
  • 描述是否准确：模型依赖描述判断什么时候调用它；
  • 参数是否结构化：参数含义和约束越明确，误调用越少；
  • 结果是否稳定：返回值应便于模型理解，异常也应有明确语义；
  • 权限是否受控：不能因为模型发起了请求就默认允许执行。

3.3 Runtime Context：运行上下文不是对话内容

Notebook 使用 ToolRuntime 和运行时 context 实现工具权限控制。这里要区分两类信息：

信息 示例 是否适合直接放入对话消息
用户要表达的内容 “帮我计算这个结果” 是
系统运行元数据 用户 ID、角色、租户、权限、追踪信息 通常否

运行上下文由应用程序可信地注入，工具可以读取其中的权限信息，再决定是否执行。这样可以避免仅凭用户在自然语言中声称“我是管理员”就获得权限。

需要注意：上下文只是把权限信息传到工具，不等于已经建立完整的安全体系。生产环境仍应在工具或下游服务中执行强制鉴权、参数校验、审计和最小权限控制。

3.4 结构化输出

自由文本适合直接展示给人，但不适合作为稳定的程序输入。结构化输出允许预先定义结果字段及其类型，使 Agent 的最终结果能够被后续程序可靠消费。

适合使用结构化输出的场景包括：

  • 信息抽取；
  • 分类和路由；
  • 计算结果；
  • 表单填充；
  • 下游 API 参数生成；
  • 需要字段校验的业务流程。

结构化输出约束的是最终结果的数据契约，并不能自动保证结果在业务语义上正确。类型校验、事实校验和业务规则校验仍然不可缺少。

3.5 流式输出

流式输出不仅能逐字展示模型文本，还可以按图的执行步骤持续返回更新。例如，调用方能够先看到模型发起工具调用，再看到工具节点返回结果，最后看到 Agent 的答案。

它的主要价值有两点：

  1. 降低用户对长任务的等待感；
  2. 暴露流程进度，便于构建执行状态界面和调试复杂 Agent。

stream_mode="updates" 更关注节点或步骤产生的状态更新；如果产品需要逐 Token 打字机效果，还需选择相应的消息流模式。两种“流式”表达的粒度并不相同。

4. StateGraph：把 Agent 还原成可控工作流

4.1 为什么需要 StateGraph

高层 Agent 会自主决定是否调用工具以及何时结束，开发简单，但控制权较多地交给了模型。

当业务要求明确规定以下内容时，更适合使用 StateGraph：

  • 必须先后执行哪些步骤；
  • 哪些分支由确定性规则决定；
  • 哪些工具可以在什么条件下使用；
  • 失败后如何重试或降级；
  • 哪一步需要人工审批；
  • 循环最多执行多少次；
  • 什么条件下必须终止。

可以把两种方式概括为：

create_agent 偏向“给模型能力，让模型在通用循环中决策”；StateGraph 偏向“由开发者定义流程，只在指定节点使用模型能力”。

4.2 State：图中的共享数据

状态是节点之间传递的数据结构。Notebook 使用 MessagesState，其核心字段是消息列表。

每个节点通常不需要返回完整状态，而是返回本次产生的状态更新。框架按照字段对应的合并规则，把更新写回当前状态。对消息状态而言，新消息通常会被追加或按消息操作规则更新。

实际项目中的状态不必只有消息，还可以包含：

  • 用户意图；
  • 当前任务阶段；
  • 检索结果；
  • 审批状态；
  • 重试次数；
  • 错误信息；
  • 最终结构化结果。

状态设计应尽量业务化。不要把所有中间信息都塞进 Prompt 或消息历史，否则流程会变得难以验证和维护。

4.3 Node：对状态执行一次转换

节点可以看成一个状态转换器：读取当前状态，完成一项职责，返回状态增量。

Notebook 中包含两类典型节点：

  • 助手节点：调用绑定了工具的模型，让模型生成回答或工具调用请求；
  • 工具节点：执行模型请求的工具，并把工具结果写回消息状态。

ToolNode 是一个预构建节点，封装了工具调用解析、执行和结果消息生成等通用逻辑。

节点应保持职责清晰。模型推理、数据库写入、权限审批、结果验证如果混在一个节点中，将很难单独测试、重试和观测。

4.4 Edge：显式表达流程关系

普通边表示无条件流转，条件边表示根据状态选择下一节点。图还使用两个特殊标识：

  • START：流程入口；
  • END：流程结束。

Notebook 中的条件判断读取模型最后一条消息：

  • 如果存在工具调用请求，则进入工具节点；
  • 如果不存在，则进入 END；
  • 工具执行完成后，再回到助手节点。

因此，该图不是有向无环图，而是一个包含循环的有向图：

flowchart TD
    S["START"] --> A["assistant：模型判断"]
    A -->|"存在 tool_calls"| T["tool：执行工具"]
    T --> A
    A -->|"无需工具"| E["END"]

循环非常适合 Agent 的“判断—行动—观察—再判断”过程，但也带来无限循环风险。生产系统应设置最大步数、超时、重复调用检测或明确的失败出口。

4.5 Build、Compile 与 Run

理解 StateGraph 可以分成三个阶段：

  1. 构建：声明状态结构、节点和边；
  2. 编译：检查并生成可运行图，同时注入 checkpointer、store 等运行能力；
  3. 运行：通过 invoke 或 stream 向图提供输入和运行配置。

图的定义是相对静态的，状态则会随着每次运行动态变化。编译后的图才是实际被调用的 Runnable。

4.6 Agent 与 Workflow 如何选择

任务特征 更适合的方式
开放式问题，步骤难以预先确定 Agent
工具数量少，允许模型自主选择 Agent
固定审批、风控或数据处理流程 StateGraph
对执行顺序和终止条件要求严格 StateGraph
大部分流程固定，局部需要自主决策 StateGraph 中嵌入 Agent/模型节点

工程中常用的是混合方案：大流程由图控制，在某个局部节点中允许模型进行有限度的自主工具调用。

5. Middleware：为 Agent 注入横切能力

5.1 中间件的定位

中间件是一组插入 Agent 生命周期的钩子。它适合实现多个节点或多个 Agent 都需要的通用能力，而不必把相同逻辑散落到每个业务节点中。

典型横切能力包括：

  • 模型路由与成本控制；
  • 上下文截断、压缩和摘要；
  • 敏感内容与隐私检测；
  • 动态系统提示词；
  • 工具权限和参数治理；
  • 日志、指标、追踪与异常处理；
  • 人机交互和审批。

5.2 常见钩子及执行位置

钩子 执行位置 适合处理
before_agent Agent 整体运行前 输入检查、拦截、初始化
after_agent Agent 整体运行后 最终审查、记录、后处理
before_model 每次模型调用前 消息裁剪、上下文注入
after_model 每次模型响应后 响应检查、指标统计
wrap_model_call 包裹整个模型调用 动态选模型、重试、降级、缓存
wrap_tool_call 包裹整个工具调用 鉴权、参数校验、超时、审计
dynamic_prompt 构造系统提示词时 按用户、环境或任务动态生成提示词

before/after 更像在某个时间点追加处理；wrap 则能控制调用前后、替换调用对象，甚至决定是否继续执行原调用。

5.3 预算控制：动态模型路由

Notebook 根据历史消息数量选择高费率或低费率模型，展示了 wrap_model_call 对模型调用的控制能力。

其核心思想不是“对话一长就一定换便宜模型”，而是根据请求特征进行路由。生产系统可以综合考虑：

  • 任务复杂度；
  • 上下文长度；
  • 用户服务等级；
  • 延迟要求；
  • 剩余预算；
  • 是否涉及高风险决策；
  • 主模型是否超时或不可用。

需要注意，简单地按消息条数判断成本并不精确。消息长度、Token 数量和工具结果大小通常比“有几条消息”更重要。

5.4 消息截断：治理上下文窗口

对话不断增长会带来上下文溢出、费用增加和注意力分散。Notebook 展示了两种策略：

  1. 保留第一条重要消息和最近若干消息；
  2. 只保留最近消息。

第二种策略会让 Agent 忘记早期的用户姓名，说明“状态被保存”不代表“每次模型都必须看到全部状态”。中间件可以在模型调用前重写模型可见的消息。

常见上下文治理策略包括：

  • 滑动窗口：只保留最近若干轮；
  • 关键消息固定保留：例如用户目标、约束、系统决策；
  • 历史摘要：把旧消息压缩成摘要；
  • 语义检索：只召回与当前问题相关的历史；
  • 分层组合：近期原文 + 早期摘要 + 长期记忆检索结果。

直接截断最简单，但也最容易丢失关键信息。业务约束、尚未完成的承诺和安全相关信息不应被无差别删除。

5.5 Guardrails：在模型外增加确定性约束

Notebook 通过 before_agent 检查最新用户输入，发现敏感关键词后直接跳转到结束节点。其关键意义是：

安全控制不应完全依赖模型自觉遵守提示词；关键规则应由运行时在模型之外强制执行。

简单关键词过滤适合作为教学示例，但生产环境还要考虑大小写、变体、上下文语义、误报、漏报和多语言表达。常见的多层防护方式是：

1

确定性规则 → 专用分类器/安全模型 → 主模型安全策略 → 输出复检

不同层的职责应明确。涉及权限、资金、数据删除等关键操作时，最终决策应由可靠的业务规则或授权系统控制，而不是只由 LLM 判断。

5.6 PII 检测：阻断与脱敏

PII 是能够识别个人身份的信息，例如姓名、电话、邮箱、证件号、地址、银行卡号、账号以及文件路径中的用户名。

Notebook 展示了两种处置方式：

  • 阻断：检测到隐私信息后拒绝继续处理；
  • 脱敏：将敏感片段替换后再展示或进入后续流程。

处置策略取决于业务目的：

场景 更适合的策略
内容没有继续处理的必要 阻断
需要保留报错结构进行调试 脱敏后继续
涉及高敏感数据且无法可靠脱敏 阻断并提示用户本地处理
合规允许且业务确实需要原文 获得授权后进入受控环境

Notebook 使用 LLM 判断和遮盖 PII，适合表达流程思想，但 LLM 检测并非完全可靠。生产环境通常还要结合正则、实体识别、专用 DLP 服务、数据分级和人工复核。

5.7 设计中间件时的原则

  • 每个中间件只负责一种清晰能力；
  • 明确它读取和修改哪些状态字段；
  • 关注多个中间件的执行顺序；
  • 避免在每次模型调用前重复执行昂贵操作；
  • 对拦截、跳转和状态重写保留审计记录；
  • 区分确定性规则与概率性模型判断；
  • 对中间件本身的异常设计降级或失败策略。

6. Memory：区分状态、短期记忆与长期记忆

6.1 最容易混淆的三个概念

概念 作用范围 典型内容 核心组件
State 当前一次图执行 消息、步骤、工具结果、临时变量 StateGraph / MessagesState
短期记忆 同一个对话线程的多次调用 会话历史、流程检查点 Checkpointer
长期记忆 跨线程、跨会话甚至长期复用 用户偏好、画像、经验、业务事实 Store

一个重要修正是：MessagesState 虽然保存消息，但如果没有 checkpointer，它通常只覆盖当前调用中的状态流转。要让下一次独立调用自动恢复此前状态，需要配置 checkpointer，并使用相同的 thread_id。

6.2 短期记忆：围绕 Thread 保存状态

短期记忆也叫线程级记忆或工作记忆。Checkpointer 会在图执行过程中保存状态快照，使同一线程后续调用可以继续使用已有状态。

thread_id 是隔离短期记忆的关键：

  • 相同 thread_id：恢复同一条对话或任务线；
  • 不同 thread_id：形成彼此隔离的对话状态；
  • 忘记传入或错误复用：可能造成记忆丢失或不同会话串线。

短期记忆不仅用于聊天历史，还支持：

  • 断点恢复；
  • 人工中断与继续执行；
  • 查看某一时刻的状态；
  • 长任务失败后的续跑；
  • 调试和回溯执行轨迹。

6.3 内存型与数据库型 Checkpointer

Notebook 对比了两种实现：

实现 特点 适用场景
InMemorySaver 使用方便，进程退出后数据消失 本地实验、单元测试、演示
SqliteSaver 状态写入 SQLite，重启后仍可恢复 本地持久化、小型应用

生产环境通常需要数据库支持的 checkpointer，并额外考虑并发、连接管理、数据清理、加密、备份和多实例部署。

“短期”描述的是记忆的语义和作用域，不代表它一定只存在于内存。SQLite 中持久化的线程状态仍然属于短期记忆，因为它服务于特定会话或任务线程。

6.4 长期记忆：围绕用户或业务实体存储信息

长期记忆不依附某一个线程，可以被多个会话检索和复用。Notebook 使用 Store 保存用户信息，并通过命名空间和键组织数据：

1
2
3

namespace：数据所属集合，例如 users
key：集合内的唯一标识，例如 user_123
value：实际保存的信息，例如姓名、职业、偏好

命名空间可以设计为多级结构，例如：

1

(tenant_id, "users", user_id, "preferences")

这样更容易实现租户隔离、用户隔离、数据分类和权限控制。

6.5 精确读取与语义检索

长期记忆通常有两种访问方式：

  • 按键读取：已知用户 ID 或记忆 ID，直接读取确定记录；
  • 语义检索：将内容转换为向量，根据当前问题召回语义相近的记忆。

例如，“我现在饿了”可能召回“我喜欢吃水煮肉片”。这不是字符串相等，而是基于向量相似度找到语义相关内容。

语义检索适合偏好、经历和非结构化事实，但不适合替代严格的数据库查询。姓名、账户状态、权限等级等确定字段，更适合按键查询或结构化过滤。

6.6 让 Agent 读取和写入长期记忆

Notebook 将 Store 传给 Agent，再通过工具读写数据。运行时上下文提供当前 user_id，工具据此访问对应用户记录。

这体现出一个重要边界：

  • 模型负责判断“现在是否值得读取或保存记忆”；
  • 工具负责按照可信上下文访问正确的数据空间；
  • 应用负责用户身份、授权、数据治理和持久化策略。

长期记忆写入不应完全无条件开放给模型。更稳妥的做法是：

  • 只保存稳定且未来有用的信息；
  • 区分用户明确陈述与模型推断；
  • 保存来源、时间和置信度；
  • 合并重复或冲突记忆；
  • 敏感信息默认不写入；
  • 支持用户查看、更正和删除；
  • 重要字段写入前进行确认或校验。

6.7 短期记忆与长期记忆如何配合 

flowchart LR
    U["当前用户请求"] --> C["短期记忆：恢复本线程状态"]
    C --> R["长期记忆：检索用户相关信息"]
    R --> M["模型生成决策或回答"]
    M --> N["更新本线程状态"]
    M -->|"发现稳定且有价值的信息"| W["写入长期记忆"]

短期记忆回答“这次对话之前发生了什么”，长期记忆回答“关于这个用户或实体，我们长期知道什么”。

7. 四个模块组合后的完整运行过程

把四份 Notebook 放在一起，一次较完整的 Agent 调用可以理解为：

flowchart TD
    I["应用提交消息、thread_id 和可信 context"] --> BA["before_agent：输入安全检查"]
    BA -->|"不允许"| X["提前结束"]
    BA -->|"允许"| CP["Checkpointer 恢复线程状态"]
    CP --> BM["before_model：裁剪或补充上下文"]
    BM --> WM["wrap_model_call：选择模型并调用"]
    WM --> D{"模型是否请求工具"}
    D -->|"否"| OUT["结构化或文本结果"]
    D -->|"是"| WT["wrap_tool_call：鉴权、校验、审计"]
    WT --> TOOL["执行工具，必要时访问 Store"]
    TOOL --> STATE["工具结果更新 State"]
    STATE --> BM
    OUT --> SAVE["保存线程检查点，必要时更新长期记忆"]
    SAVE --> AFT["after_agent：审查、日志和指标"]

这张图也说明了各组件的职责边界：

  • StateGraph 决定流程如何运行；
  • Agent/模型负责需要语言理解和动态决策的部分；
  • Middleware 管理调用生命周期中的通用策略；
  • Checkpointer 保存线程状态；
  • Store 保存跨线程的长期信息；
  • Context 向运行时提供可信的身份和环境信息。

8. 常见误区

8.1 “用了 MessagesState 就自动拥有多轮记忆”

不完全正确。消息状态能在当前图执行中流转；独立调用之间要自动延续状态，还需要 checkpointer 和稳定的 thread_id。

8.2 “长期记忆就是把全部聊天记录放进向量库”

长期记忆应该保存经过筛选、未来有用的信息。无差别保存会造成噪声、隐私风险、检索漂移和存储成本上升。

8.3 “工具调用由模型决定，所以权限也可以交给模型判断”

错误。模型可以建议调用工具，但真正的权限验证必须由受信任的运行时、工具实现或下游服务完成。

8.4 “中间件越多，系统能力越强”

中间件会增加调用链复杂度、延迟和状态修改冲突。只应加入有明确职责、可测试、可观测的中间件，并设计好执行顺序。

8.5 “StateGraph 只能创建固定工作流”

图的结构由开发者定义，但条件边、循环、模型节点和动态路由仍能提供很强的运行时灵活性。它是“受控的动态流程”，不只是线性流水线。

8.6 “结构化输出等于答案可靠”

结构化输出只保证结果更符合数据格式，不保证事实、计算或业务判断一定正确。可靠性仍需要工具、验证节点和业务规则共同保证。

10. 大厂 AI Agent 岗位面试要点

10.1 一分钟讲清 LangGraph

面试中可以这样概括：

LangGraph 是面向有状态 Agent 工作流的编排与运行框架。它用 State、Node 和 Edge 描述执行过程，支持条件分支、循环、流式输出、状态持久化和人工中断。与直接使用高层 Agent 相比，LangGraph 的优势是流程更可控，执行状态更容易持久化、观测和恢复，适合构建生产级多步骤 Agent 系统。

回答时应突出五个关键词：有状态、可控循环、持久化、可恢复、可观测。

10.2 LangChain、LangGraph 与 Agent 的关系

这是常见的概念辨析题：

  • LangChain 提供模型、消息、工具、检索器、中间件和 Agent 等上层组件；
  • LangGraph 更关注有状态工作流的编排和运行；
  • Agent 是一种应用形态，模型能够根据当前状态动态决定下一步行动；
  • create_agent 是高层入口，其底层运行机制可以建立在 LangGraph 之上。

不要简单回答“LangChain 是链，LangGraph 是图”。更准确的区别在于：LangGraph 重点解决循环、分支、持久状态、恢复和人机协同等运行时问题。

10.3 Agent 与 Workflow 的边界

高频问题：什么时候使用 Agent，什么时候使用确定性工作流？

推荐回答框架：

  1. 能用确定性规则稳定完成的步骤，优先使用普通代码或固定工作流；
  2. 只有在需要理解自然语言、处理开放环境或动态选择工具时，才引入模型决策；
  3. 高风险操作必须经过规则校验或人工审批；
  4. 生产系统通常采用“外层确定性图 + 局部 Agent 节点”的混合架构。

核心原则是：

把模型放在需要概率性判断的位置，而不是让模型控制所有流程。

10.4 State 为什么不能只是消息列表

MessagesState 适合聊天和简单工具调用，但复杂业务还应定义显式字段，例如意图、计划、检索结果、审批状态、重试次数和最终结果。

面试官可能继续追问状态如何合并。LangGraph 中节点通常返回状态增量，每个字段按照对应的 Reducer 进行合并：

  • 覆盖型字段保存最新值；
  • 消息字段可以追加、删除或更新消息；
  • 列表、计数器等字段可定义自己的合并语义。

如果状态更新语义不明确，并行分支或循环执行时就容易出现覆盖、重复和脏数据问题。

10.5 为什么图中允许循环，如何防止死循环

Agent 需要根据工具结果继续决策，因此“模型节点—工具节点”天然是循环结构。

生产环境至少应配置：

  • 最大递归或执行步数；
  • 单次任务总超时；
  • 单工具调用超时和重试上限；
  • 重复工具调用与重复参数检测；
  • Token 或费用预算；
  • 明确的失败、降级和人工接管出口。

仅依靠提示词要求模型“不要无限循环”是不可靠的。

10.6 Checkpointer 与 Store 的区别

这是记忆模块最常见的面试题：

对比项 Checkpointer Store
作用域 某个执行线程 跨线程的用户或业务实体
典型索引 thread_id namespace + key
主要内容 图状态、消息、执行位置 偏好、画像、经验和长期事实
典型用途 多轮对话、断点恢复、人工中断 个性化、跨会话记忆、经验复用

一句话回答：

Checkpointer 保存“这条任务执行到了哪里”，Store 保存“系统长期知道什么”。

10.7 thread_id、user_id 与 tenant_id

这三个 ID 不应混用：

  • thread_id 标识一次持续的对话或任务；
  • user_id 标识用户，用于读取用户级长期记忆；
  • tenant_id 标识组织或租户，用于权限和数据隔离。

一个用户可以拥有多个线程，一个租户可以拥有多个用户。生产系统的记忆命名空间和数据库查询必须同时考虑用户与租户隔离，不能只相信模型生成的 ID。

10.8 Middleware 与普通 Node 有什么区别

  • Node 是业务流程中的显式步骤，会出现在图结构中；
  • Middleware 是模型、工具或 Agent 生命周期中的横切逻辑；
  • 业务特有且需要清晰流转的逻辑适合做 Node；
  • 鉴权、日志、模型路由、重试和上下文裁剪等通用能力适合做 Middleware。

如果某段中间件逻辑逐渐拥有复杂状态、多个分支或独立重试策略，就应考虑将其升级为显式节点或子图。

10.9 如何设计生产级工具

面试时不要只回答“写一个带类型注解的函数”。生产级工具还应具备：

  • 清晰的名称、职责和参数 Schema；
  • 服务端鉴权，而非让模型判断权限；
  • 参数白名单、范围校验和防注入处理；
  • 超时、有限重试、幂等和熔断；
  • 结构化成功结果与错误类型；
  • 调用日志、延迟、费用和结果审计；
  • 写操作预览、用户确认或人工审批；
  • 对工具返回内容中的 Prompt Injection 进行隔离和防护。

对于转账、删除、发邮件等有副作用的工具，必须重点说明幂等性、确认机制和最小权限。

10.11 Human-in-the-loop 如何设计

LangGraph 的检查点与中断机制适合实现人工审批：流程运行到高风险节点时暂停并保存状态，人工提交审批结果后再从原状态继续。

设计时需要回答：

  • 在哪些风险等级触发中断；
  • 审批页面展示哪些上下文和待执行动作；
  • 谁拥有审批权限；
  • 审批结果如何防篡改并写入审计日志；
  • 超时未审批时如何取消或降级；
  • 恢复执行时如何避免副作用工具被重复调用。

10.12 如何评估一个 Agent 系统

不能只看最终答案“像不像正确”。应分层评估：

层次 典型指标
任务结果 成功率、正确率、约束满足率
轨迹质量 工具选择准确率、参数正确率、无效步骤数
检索与记忆 Recall、Precision、错误记忆引用率
安全 越权调用率、敏感信息泄露率、误拦截率
工程性能 P50/P95 延迟、Token、费用、超时率
稳定性 重试率、死循环率、人工接管率

评测集应包含正常样本、边界样本、对抗样本、工具异常和历史记忆冲突等情况。线上指标负责发现真实分布问题，离线回归集负责保证版本迭代不退化。

10.13 项目经历的表达方式

介绍 LangGraph 项目时，可以按以下顺序展开：

  1. 业务目标：解决了谁的什么问题；
  2. 为什么需要 Agent：哪些步骤无法完全规则化；
  3. 图结构：核心节点、条件分支、循环和终止条件；
  4. 工具与数据：工具如何鉴权、检索和处理异常；
  5. 状态与记忆：如何划分 State、Checkpointer 和 Store；
  6. 可靠性：如何控制幻觉、死循环、超时和副作用；
  7. 评测结果：成功率、延迟、成本或人工效率提升；
  8. 复盘优化：遇到过什么失败案例，后来如何改进。

避免只说“使用 LangGraph 搭建了 Agent”。面试官更关心架构选择的原因、失败处理和可量化结果。

10.15 面试中的加分观点

  • Agent 的核心难点不是“能调用工具”，而是在不确定模型之上建立确定性的工程边界；
  • Prompt 只是系统的一层，可靠性还来自状态建模、权限、验证、重试、记忆治理和评测；
  • 复杂 Agent 应尽量缩小单个模型节点的决策空间；
  • 长期记忆是一套数据治理能力，不只是向量数据库；
  • 能用普通程序解决的问题，不要为了 Agent 化而 Agent 化；
  • 生产效果的优化目标通常是质量、延迟、成本和安全之间的平衡，而不是单独追求模型能力。

流程控制

  • 模型决策与确定性业务规则是否分离；
  • 节点是否职责单一并可单独测试；
  • 工具失败、返回空结果或重复调用时是否有降级策略。

安全

  • 工具是否执行服务端鉴权和参数校验；
  • 用户输入、工具返回和模型输出是否分别进行安全处理；
  • PII 是否遵循最小收集、脱敏、加密和删除策略；
  • 高风险写操作是否需要二次确认或人工审批。

记忆

  • thread_id、user_id 和 tenant_id 是否正确隔离；
  • 哪些信息进入短期记忆，哪些信息允许进入长期记忆；
  • 是否记录记忆来源、时间、置信度和过期规则；
  • 用户是否能够查看、更正和删除长期记忆。

成本与性能

  • 是否监控 Token、模型调用次数、工具耗时和总延迟；
  • 上下文是否有裁剪、摘要或检索策略；
  • 模型路由是否基于真实复杂度和服务等级；
  • 昂贵中间件是否被重复执行。

可观测性

  • 是否记录每个节点的输入摘要、输出摘要、耗时和异常；
  • 是否能通过 thread/run 标识关联一条完整执行链；
  • 是否区分模型错误、工具错误、业务拒绝和系统错误；
  • 是否有离线评测集验证路由、安全、记忆和最终答案质量。

12. 总结

可以用下面几句话记住这四部分：

  1. Agent 提供一个开箱即用的“模型—工具—观察”循环；
  2. StateGraph 用状态、节点和边把这个循环变成可显式控制的工作流；
  3. Middleware 在 Agent 生命周期中统一注入成本、上下文、安全和可观测性策略；
  4. Checkpointer 保存同一线程的短期状态，Store 保存跨线程复用的长期信息；
  5. 模型负责概率性的理解与决策，运行时和业务系统负责确定性的权限、规则与数据治理。

LangGraph 的核心思路可以最终归纳为：

用图控制流程，用状态承载上下文，用工具连接外部世界，用中间件治理运行过程，用记忆延续有价值的信息。
