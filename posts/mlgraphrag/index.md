# GraphRAG


## 1. 一分钟面试回答

Graph RAG 是在传统 RAG 的向量检索之外，引入图结构来表示和检索知识。

传统 RAG 通常把文档切成相互独立的 Chunk，根据 Query 与 Chunk 的向量相似度召回 Top-K。它适合查找局部事实，但面对跨文档、多跳关系、全局总结和复杂关系推理时，容易漏掉“单个 Chunk 不够相似、但通过关系连接后很重要”的信息。

Graph RAG 的典型做法是：

1. 在索引阶段从文档中抽取实体、关系和关键事件，构建知识图谱。
2. 使用 Leiden 等社区发现算法，把紧密关联的实体划分为不同层级的社区。
3. 为社区生成摘要，并对文本块、实体、关系、社区摘要建立向量索引。
4. 查询时先判断问题类型：
   - 局部事实问题走实体检索和邻域扩展；
   - 全局总结问题走社区摘要检索和 Map-Reduce；
   - 混合问题结合向量搜索、关键词搜索和图遍历。
5. 将检索到的证据、关系路径和来源组织成上下文，再交给 LLM 生成带引用的答案。

一句话概括：

&gt; 传统 RAG 主要回答“哪些文本和问题相似”，Graph RAG 进一步回答“这些知识之间如何连接”。

## 2. 为什么需要 Graph RAG

### 2.1 传统 RAG 的局限

传统向量 RAG 的基本流程是：

```text
Query → Query Embedding → 向量 Top-K → 拼接 Chunks → LLM 生成
```

它主要存在以下问题：

1. **Chunk 相互孤立**：向量库通常不知道两个文本块之间存在因果、隶属、合作或时间关系。
2. **多跳问题召回困难**：答案需要经过 A → B → C 才能得到，但 B、C 与原始 Query 的直接相似度可能不高。
3. **全局问题表现较差**：例如“整个知识库的主要主题和核心矛盾是什么”，答案分散在大量文档中，不适合直接 Top-K。
4. **实体歧义**：同名实体、别名、缩写可能导致错误召回或知识割裂。
5. **上下文碎片化**：召回的 Chunk 看似相关，但彼此不连贯，LLM 需要自己猜测它们的关系。
6. **可解释性有限**：只能展示引用文本，难以解释证据之间的推理链路。

### 2.2 Graph RAG 的核心价值

Graph RAG 通过节点、边、社区和路径补充结构信息：

| 能力 | 向量 RAG | Graph RAG |
| --- | --- | --- |
| 局部语义事实检索 | 强 | 强 |
| 精确实体关系查询 | 一般 | 强 |
| 跨文档多跳推理 | 较弱 | 强 |
| 全库主题总结 | 较弱 | 社区摘要方案较强 |
| 新知识接入成本 | 较低 | 较高 |
| 索引成本 | 较低 | 较高 |
| 查询延迟 | 较低 | 通常更高 |
| 可解释性 | 文本引用 | 文本引用 &#43; 关系路径 |

Graph RAG 不是用图数据库完全替代向量数据库。工业系统通常是：

```text
向量检索负责“语义召回”
关键词检索负责“精确匹配”
图检索负责“关系扩展与结构约束”
Reranker 负责“候选精排”
```

## 3. Graph RAG 的两类常见图模型

“Graph RAG”不是唯一固定算法，面试时应先说明图的节点和边是什么。

### 3.1 实体关系图：标准知识图谱式 Graph RAG

节点通常是人物、组织、地点、产品、事件和概念，边表示实体之间的语义关系。

```text
(张三)-[任职于]-&gt;(A 公司)
(A 公司)-[研发]-&gt;(产品 X)
(产品 X)-[依赖]-&gt;(模型 Y)
```

优点：

- 关系语义明确，适合精确查询和多跳推理。
- 可以使用 Cypher、Gremlin 等图查询语言。
- 便于做实体消歧、关系过滤和路径解释。
- 可以通过社区检测和社区摘要支持全局检索。

缺点：

- 实体和关系抽取依赖 LLM，成本高且存在错误传播。
- Schema、实体对齐和冲突消解的工程复杂度高。
- 图谱更新、版本管理和权限控制比纯向量库复杂。

### 3.2 文本块图：当前 Notebook 的实现

当前 Notebook 中：

- 每个节点是一个文本 Chunk；
- 节点属性包含原文和抽取出的实体/概念；
- 当两个 Chunk 的向量相似度超过阈值时建立无向边；
- 边权同时考虑向量相似度和共享概念比例。

```text
Chunk A --[相似度 &#43; 共享概念]-- Chunk B
```

优点：

- 不需要预先定义复杂的实体关系 Schema。
- 易于从普通 RAG 平滑升级。
- 可以从向量召回的 Chunk 出发，沿图找到语义关联内容。

缺点：

- 边只有强弱，没有清晰的关系类型。
- 图规模与 Chunk 数量直接相关，容易形成稠密图。
- 对精确实体关系查询不如实体关系图。
- 不具备典型社区摘要 GraphRAG 的全局检索能力。

### 3.3 面试中的标准表达

如果面试官问“你的 Graph RAG 中图是怎么构建的”，不能只回答“用知识图谱”。应该依次说明：

1. 节点是什么；
2. 边是什么；
3. 边是否有方向和类型；
4. 边权如何计算；
5. 图存在哪里；
6. 查询时如何确定起点、扩展范围和停止条件。

## 4. 总体架构：离线索引与在线查询

Graph RAG 仍然可以拆成两条链路。

```mermaid
flowchart TB
    subgraph Indexing[&#34;索引阶段：离线或准实时&#34;]
        A[&#34;PDF / Word / 网页 / 数据库&#34;] --&gt; B[&#34;解析、清洗与切块&#34;]
        B --&gt; C[&#34;实体、关系、事件、概念抽取&#34;]
        C --&gt; D[&#34;实体对齐、去重、消歧&#34;]
        D --&gt; E[&#34;构建实体关系图或文本块图&#34;]
        E --&gt; F[&#34;社区检测：Leiden&#34;]
        F --&gt; G[&#34;社区分层与摘要生成&#34;]
        B --&gt; H[&#34;Chunk Embedding&#34;]
        C --&gt; I[&#34;实体/关系 Embedding&#34;]
        G --&gt; J[&#34;社区摘要 Embedding&#34;]
        H --&gt; K[&#34;向量索引&#34;]
        I --&gt; K
        J --&gt; K
        E --&gt; L[&#34;图数据库&#34;]
    end

    subgraph Querying[&#34;查询阶段：在线&#34;]
        Q[&#34;用户 Query&#34;] --&gt; R[&#34;意图识别、实体链接、问题拆解&#34;]
        R --&gt; S{&#34;查询路由&#34;}
        S --&gt;|局部问题| T[&#34;实体检索 &#43; 邻域扩展&#34;]
        S --&gt;|全局问题| U[&#34;社区摘要检索 &#43; Map-Reduce&#34;]
        S --&gt;|混合问题| V[&#34;向量 &#43; 关键词 &#43; 图检索&#34;]
        K --&gt; T
        K --&gt; U
        K --&gt; V
        L --&gt; T
        L --&gt; V
        T --&gt; W[&#34;候选融合、去重与 Rerank&#34;]
        U --&gt; W
        V --&gt; W
        W --&gt; X[&#34;上下文构造与动态 Prompt&#34;]
        X --&gt; Y[&#34;LLM 生成&#34;]
        Y --&gt; Z[&#34;答案、引用和关系路径&#34;]
    end
```

## 5. 索引阶段详解

### 5.1 文档解析、清洗与切块

索引的第一步与普通 RAG 相同：

1. 解析 PDF、网页、Word、数据库记录等数据源。
2. 清理页眉页脚、乱码、重复内容和无效格式。
3. 保留标题层级、页码、时间、作者、权限等元数据。
4. 将长文档切分为适合抽取和检索的 Chunk。

课程图给出的示例参数是约 `1200 tokens &#43; 100 tokens overlap`。但当前 Notebook 实际使用：

```python
RecursiveCharacterTextSplitter(
    chunk_size=1200,
    chunk_overlap=100,
)
```

这里默认按 Python 字符长度计算，不是严格按 Token 计算。因此准确描述应是“1200 字符、重叠 100 字符左右”。如果生产环境要求精确控制模型上下文，需要传入基于 tokenizer 的 `length_function`。

切块的主要权衡：

- 太小：实体关系被截断，图谱抽取缺少上下文；
- 太大：抽取成本提高，Chunk 向量语义被稀释；
- Overlap 太小：跨块关系丢失；
- Overlap 太大：重复实体、重复关系和索引膨胀。

生产中可以采用标题感知、语义切分或父子块策略，而不是只使用固定长度。

### 5.2 实体、关系、概念和事件抽取

典型实体关系抽取结果可以表示为：

```json
{
  &#34;entities&#34;: [
    {&#34;name&#34;: &#34;IPCC&#34;, &#34;type&#34;: &#34;ORG&#34;},
    {&#34;name&#34;: &#34;greenhouse gases&#34;, &#34;type&#34;: &#34;CONCEPT&#34;}
  ],
  &#34;relationships&#34;: [
    {
      &#34;source&#34;: &#34;greenhouse gases&#34;,
      &#34;target&#34;: &#34;climate change&#34;,
      &#34;type&#34;: &#34;CAUSES&#34;,
      &#34;evidence&#34;: &#34;...&#34;,
      &#34;source_id&#34;: &#34;doc-1#page-1#chunk-2&#34;
    }
  ]
}
```

当前 Notebook 使用两种方式抽取节点概念：

1. spaCy 抽取 `PERSON`、`ORG`、`GPE`、`WORK_OF_ART` 等命名实体；
2. LLM 通过结构化输出抽取通用概念；
3. 将命名实体与通用概念去重后，写入 Chunk 节点的 `concepts` 属性。

```python
all_concepts = list(set(named_entities &#43; general_concepts))
```

这里并没有把实体本身创建为独立节点，也没有抽取 `source-relation-target` 三元组，所以它更准确地说是“带概念属性的文本块图”。

### 5.3 实体标准化、对齐和消歧

抽取之后必须解决同一实体的不同写法：

```text
阿里 / 阿里巴巴 / Alibaba Group
北京大学 / 北大 / PKU
苹果：公司还是水果？
```

常见策略：

- 大小写、空格、符号和词形归一化；
- 别名词典与业务主数据 ID；
- 字符串相似度 &#43; Embedding 相似度；
- 根据实体类型和邻接关系进行消歧；
- LLM 判断候选实体是否应合并；
- 低置信度实体进入人工审核队列。

当前 Notebook 定义了 `_lemmatize_concept()`，但建边计算共享概念时使用的是未归一化的原始字符串。词形还原只在查询遍历期间用于 `visited_concepts`，因此 `cars` 与 `car` 在建边时仍可能被当作不同概念。

### 5.4 图构建与边权设计

当前 Notebook 首先为每个 Chunk 创建一个 NetworkX 节点：

```python
self.graph.add_node(i, content=split.page_content)
```

然后计算所有 Chunk 两两之间的余弦相似度。只有满足：

```text
cosine_similarity(i, j) &gt; 0.8
```

才建立无向边。

边权公式为：

```text
weight(i, j) = α × semantic_similarity(i, j)
             &#43; β × normalized_shared_concepts(i, j)
```

Notebook 中：

```text
α = 0.7
β = 0.3

normalized_shared_concepts = 共享概念数量 / 两节点概念数量的较小值
```

这个设计表达了两个信号：

- Chunk 整体语义是否相似；
- Chunk 是否显式共享相同实体或概念。

需要注意：当前实现先使用 `similarity &gt; 0.8` 做硬过滤，再计算共享概念。因此两个向量相似度不高但共享关键实体的 Chunk，不会建立边。生产中可以分别建立多种边：

```text
NEXT_CHUNK       文档顺序边
SAME_ENTITY      共享实体边
SEMANTIC_SIMILAR 语义相似边
REFERENCES       引用边
CAUSES           因果关系边
BELONGS_TO       隶属关系边
```

这样可以根据 Query 类型选择不同的扩展规则，而不是把所有关系压缩成一个权重。

### 5.5 社区检测：为什么常用 Leiden

完整 GraphRAG 通常会对实体关系图做社区发现。社区是一组内部连接紧密、与外部连接相对稀疏的节点。

Leiden 算法的目标通常是优化模块度或 CPM 质量函数。它相比 Louvain 的重要改进是会进一步细化社区，使社区内部具有更好的连通性，结果通常更稳定。

社区检测的作用：

1. 把大图划分为有业务含义的主题子图；
2. 建立从细粒度到粗粒度的社区层级；
3. 为每个社区生成摘要，压缩大量节点和边；
4. 支持“整个知识库有哪些主题”一类全局问题。

```text
实体/关系图
  ├── 一级社区：能源
  │     ├── 二级社区：化石燃料
  │     └── 二级社区：可再生能源
  └── 一级社区：气候影响
        ├── 二级社区：海平面
        └── 二级社区：极端天气
```

当前 Notebook 没有实现 Leiden/Louvain 社区检测，也没有社区层级和社区摘要。这是它与课程第三张图最明显的差异。

### 5.6 社区摘要生成

社区摘要通常包含：

- 社区的主要实体；
- 实体之间的重要关系；
- 关键事件和时间线；
- 主题、矛盾和代表性事实；
- 原始证据的来源 ID；
- 社区重要性和置信度。

社区摘要的价值是把“检索几百个节点”转换为“检索少量结构化报告”。但摘要也会带来信息损失和幻觉风险，因此必须保留从摘要到实体、关系、Chunk 和原文的映射。

### 5.7 多路索引与存储

生产 Graph RAG 往往同时维护：

| 索引/存储 | 保存内容 | 主要用途 |
| --- | --- | --- |
| 向量库 | Chunk、实体描述、关系描述、社区摘要向量 | 语义召回 |
| 关键词索引 | 原文、实体名、ID、专有名词 | 精确匹配与 BM25 |
| 图数据库 | 节点、边、属性、路径 | 邻域扩展与多跳查询 |
| 文档库/对象存储 | 原始文档和解析结果 | 证据回溯 |
| 元数据数据库 | 权限、版本、时间、租户 | 过滤和治理 |

当前 Notebook 使用：

- FAISS：保存 Chunk 向量；
- NetworkX：在单机内存中保存文本块图；
- 没有使用 Neo4j、NebulaGraph、JanusGraph 等图数据库；
- 没有持久化图索引，进程重启后需要重新抽取和建图。

## 6. 查询阶段详解

### 6.1 Query 分析与路由

课程查询图把问题分成三类：

| 查询类型 | 例子 | 主要检索方式 |
| --- | --- | --- |
| 简单局部查询 | “张三在哪家公司工作？” | 向量/关键词召回 &#43; 1 跳邻域 |
| 复杂关系查询 | “A 公司通过哪些合作伙伴影响产品 X？” | 实体链接 &#43; 多跳图遍历 |
| 全局查询 | “知识库的主要主题和风险是什么？” | 社区摘要 &#43; Map-Reduce |
| 混合查询 | “新能源政策如何通过供应链影响公司 X？” | 子问题拆解 &#43; 向量和图联合检索 |

查询分析通常包括：

1. 意图分类；
2. 实体和时间范围识别；
3. 实体链接到图节点；
4. Query Rewrite 和同义词扩展；
5. 复杂问题拆分；
6. 决定检索器、跳数、Top-K、过滤条件和 Token 预算。

### 6.2 Local Search：局部实体与邻域检索

Local Search 适合回答围绕具体实体的事实和关系问题。

```mermaid
flowchart LR
    A[&#34;Query&#34;] --&gt; B[&#34;识别并链接实体&#34;]
    B --&gt; C[&#34;找到种子节点&#34;]
    C --&gt; D[&#34;1~N 跳邻域扩展&#34;]
    D --&gt; E[&#34;实体、关系、原始 Chunk&#34;]
    E --&gt; F[&#34;去重、打分和 Rerank&#34;]
    F --&gt; G[&#34;构造上下文并生成答案&#34;]
```

常见排序信号：

```text
final_score = w1 × query_vector_similarity
            &#43; w2 × entity_match_score
            &#43; w3 × path_relevance
            &#43; w4 × edge_confidence
            &#43; w5 × source_quality
            &#43; w6 × freshness
            - w7 × path_length
```

图扩展不能只设置固定跳数，还应限制：

- 节点类型和关系类型；
- 最大节点数量和最大路径数量；
- 时间范围、租户和权限；
- 边置信度阈值；
- 总 Token 预算。

否则高连接度 Hub 节点会造成候选爆炸。

### 6.3 Global Search：社区摘要与 Map-Reduce

Global Search 适合全库总结、主题发现和宏观分析。

典型流程：

1. 根据 Query 检索相关社区摘要；
2. 在多个社区上并行执行 Map：分别生成局部答案和重要性评分；
3. 丢弃低相关局部答案；
4. Reduce：综合多个社区答案，生成全局结论；
5. 回溯社区中的原始证据并添加引用。

```text
Query
  → 社区摘要 Top-K
  → [社区 A 局部回答, 社区 B 局部回答, 社区 C 局部回答]
  → 评分、压缩和合并
  → 全局回答
```

它的优势是覆盖面广，缺点是索引和查询 LLM 调用较多，成本较高，而且社区摘要可能丢失细节。

### 6.4 Hybrid Search：向量、关键词和图联合检索

实际系统很少只使用一种检索方式：

- 向量检索：处理自然语言语义和同义表达；
- BM25/关键词：处理产品号、人名、错误码和缩写；
- 图查询：处理关系、路径和结构约束；
- 社区摘要：处理全局主题；
- SQL/API：处理实时、精确的结构化数据。

多路检索结果分数不可直接比较。常见融合方式包括：

- Reciprocal Rank Fusion（RRF）；
- 分数归一化后加权；
- Learning to Rank；
- Cross-Encoder 或 LLM Reranker。

RRF 公式：

```text
RRF(d) = Σ 1 / (k &#43; rank_i(d))
```

它只依赖候选在不同检索器中的排名，适合融合量纲不同的结果。

### 6.5 动态 Prompt 工程

检索完成后，不应直接把所有节点和边无序拼接给 LLM。可以将上下文组织为：

```text
[任务要求]
仅根据证据回答；证据不足时明确说明；引用 source_id。

[用户问题]
...

[关键实体]
- entity_id / name / type / description

[关键关系]
- source --relation--&gt; target / confidence / source_id

[关系路径]
- A -&gt; B -&gt; C

[原始证据]
- source_id / title / page / chunk text

[输出格式]
- 结论
- 推理依据
- 引用来源
- 不确定项
```

动态 Prompt 可以根据查询类型选择不同模板，例如局部事实模板、路径推理模板和全局总结模板。

### 6.6 引用与可解释性

Graph RAG 的可解释性不应只展示一条图路径。完整的证据链应该是：

```text
答案
  → 使用了哪些实体和关系
  → 每条关系来自哪个 Chunk
  → Chunk 来自哪个文档、页码和版本
```

关系路径是“检索和推理线索”，原始文本才是最终证据。LLM 抽取出的边本身可能出错，不能脱离原文作为绝对事实。

```mermaid

    I --&gt; J{&#34;队列是否为空&#34;}
    J --&gt;|否| F
    J --&gt;|是| K[&#34;使用累计上下文生成兜底答案&#34;]
```

Notebook 先进行向量召回：

```python
retriever = self.vector_store.as_retriever(
    search_type=&#34;similarity&#34;,
    search_kwargs={&#34;k&#34;: 5},
)
```

再使用 `LLMChainExtractor` 只保留与 Query 有关的句段。随后以召回结果对应的 Chunk 作为种子节点，通过最小堆遍历图。

图上的路径代价为：

```text
new_distance = current_distance &#43; 1 / edge_weight
```

边权越大，新增距离越小，因此算法倾向优先探索强连接路径。

每加入一个节点后，都会让 LLM 判断当前上下文能否完整回答。如果可以则提前停止，否则继续扩展；队列耗尽后使用累计上下文生成答案。

1. 同时使用向量召回与图扩展，展示了 Hybrid Graph RAG 的基本思路。
2. 使用结构化输出约束概念抽取和答案完整性判断。
3. 使用多线程并行抽取各 Chunk 的概念。
4. 边权融合向量相似度和共享概念两个信号。
5. 支持可视化实际遍历路径，便于调试和解释。
6. 统计 Token 和调用成本，具有一定工程意识。

## 8. 当前实现的关键问题与优化方向

这部分非常适合面试中的“项目复盘”和“如果让你重新设计”问题。

### 8.1 建图复杂度是 O(N²)

当前代码生成完整的 `N × N` 相似度矩阵，并使用双重循环判断所有 Chunk 对：

```text
时间复杂度：O(N² × d)
空间复杂度：O(N²)
```

其中 `d` 是向量维度。Chunk 数量达到十万级时不可行。

优化方式：

- 使用 FAISS/HNSW 为每个节点只找近邻 Top-K；
- 仅在同文档、同实体、同时间窗口等候选集合内建边；
- 对高频实体限流，避免超级节点；
- 批量写入图数据库；
- 离线增量建图，而不是每次全量重算。

优化后边数量可以从 `O(N²)` 降到近似 `O(NK)`。

### 8.2 FAISS 的 score 语义需要确认

LangChain FAISS 的 `similarity_search_with_score()` 通常返回距离，常见情况下越小越相似，而不是越大越相似。

当前代码执行：

```python
priority = 1 / similarity_score
heapq.heappush(priority_queue, (priority, closest_node))
```

最小堆优先弹出数值更小的元素。如果 `similarity_score` 实际是距离，那么“距离越大，倒数越小，反而越先出队”，排序方向可能被反转；当距离接近 0 时还存在除零风险。

更稳妥的实现是：

1. 明确向量库返回的是距离还是相似度；
2. 如果是距离，直接使用非负距离作为最小堆优先级；
3. 如果是相似度，转换为 `1 - similarity` 或 `-similarity`；
4. 使用 `max(score, epsilon)` 避免除零；
5. 用单元测试验证“最相似节点最先出队”。

### 8.3 当前算法不是严格的 Dijkstra

代码在发现邻居时就立刻把邻居加入 `traversal_path` 和上下文，而不是等待邻居真正从优先级队列弹出后再访问。这会导致：

- 上下文顺序不完全服从全局最短路径优先级；
- 低优先级邻居可能被过早加入上下文；
- `traversal_path` 更像“发现顺序”，不完全是“出队访问顺序”。

生产实现应把“发现候选”和“正式访问”分开，节点在从堆中弹出并确认是最佳路径后，才加入上下文。

### 8.4 上下文长度没有真正受控

`QueryEngine` 定义了：

```python
self.max_context_length = 4000
```

但后续没有使用。随着图扩展，`expanded_context` 会持续增长，可能超过 LLM 上下文预算，并产生重复信息。

优化方式：

- 按 tokenizer 统计 Token，而不是字符数；
- 在每次扩展前检查剩余预算；
- 对候选做 MMR 和去重；
- 只抽取与 Query 相关的证据句；
- 使用父子块：小块检索，大块补充上下文；
- 对路径或社区先摘要再放入 Prompt。

### 8.5 每个节点都调用 LLM，成本和延迟较高

当前遍历每加入一个节点或邻居，就调用一次 `_check_answer()`。当遍历节点较多时，会产生大量串行 LLM 请求。

可选优化：

- 每扩展一批节点后再判断一次；
- 先使用轻量分类器或规则估计证据完整性；
- 设置最少证据数、最大跳数和最大 LLM 检查次数；
- 并行评估多个候选路径；
- 使用一个最终 Rerank &#43; Answerability 模型替代逐节点判断；
- 缓存相同 Query/上下文摘要的判断结果。

### 8.6 压缩后的文档与图节点需要二次映射

`LLMChainExtractor` 会改变原始 `page_content`。当前代码只能再次做向量检索，把压缩结果映射回图中的原始 Chunk。

更可靠的方式是从一开始保留稳定 ID：

```text
document_id / page / chunk_id / entity_id / relation_id
```

压缩、Rerank 和图扩展过程中都传递 ID，不依赖文本内容相等或二次近似匹配。

### 8.7 缺少来源、页码和置信度

图节点目前只保存 `content` 和 `concepts`，没有保存原始 `Document.metadata`。因此最终答案无法可靠返回文档名、页码和 Chunk ID。

生产图节点和边至少应保存：

```text
node: id, type, name/content, source_id, page, tenant, version, acl
edge: type, confidence, source_id, extractor_version, created_at
```

### 8.8 图边缺少关系类型和方向

当前使用 `nx.Graph()` 构建无向图，并把语义相似性和共享概念压缩为一个数值。这不适合表达：

```text
A 收购 B
B 收购 A
```

两者方向完全不同。生产知识图谱通常使用有向多重图，并保留关系类型、时间和置信度。

### 8.9 缺少社区检测和全局搜索

课程图中的“社区检测 → 社区摘要 → 摘要 Embedding → 全局检索”未在 Notebook 中实现。

补全方案：

1. 从实体关系三元组构建实体图；
2. 使用 Leiden 生成分层社区；
3. 为每个社区生成可追溯摘要；
4. 对摘要建立向量索引；
5. 实现 Local、Global 和 Hybrid 查询路由；
6. Global Search 使用 Map-Reduce 聚合社区答案。

### 8.10 增量更新和删除较困难

如果原文更新，需要回答：

- 哪些 Chunk 需要重建？
- 哪些实体和关系由旧版本文档产生？
- 删除一份文档后，某条边是否还有其他证据支持？
- 社区划分和摘要是否需要重算？

生产设计应使用稳定 ID、文档版本、关系证据计数和可回溯 lineage。更新时先定位受影响的局部子图，再执行局部重建和社区摘要刷新。

## 9. 生产级 Graph RAG 设计

### 9.1 推荐的数据模型

```text
Document
  └── Section
        └── Chunk
              ├── MENTIONS → Entity
              └── EVIDENCE_FOR → Relation

Entity -[typed relation]-&gt; Entity
Entity -[BELONGS_TO]-&gt; Community
Community -[PARENT_OF]-&gt; Community
Community -[HAS_REPORT]-&gt; CommunityReport
```

这样可以同时支持：

- Chunk 级向量召回；
- 实体精确查询；
- 多跳关系遍历；
- 社区级全局总结；
- 从结论回溯到原始文档。

### 9.2 索引服务拆分

```text
数据接入
  → 解析/OCR
  → 清洗与切块
  → 实体关系抽取
  → 实体对齐与冲突消解
  → 图写入
  → 向量索引
  → 社区检测
  → 社区摘要
  → 质量校验与发布
```

大规模系统可以使用消息队列解耦各阶段，并为每个阶段记录状态、重试次数和模型版本。

### 9.3 在线查询服务拆分

```text
Query Gateway
  → Query Understanding
  → Retrieval Router
      ├── Vector Retriever
      ├── Keyword Retriever
      ├── Graph Retriever
      └── Community Retriever
  → Fusion &amp; Rerank
  → Context Builder
  → LLM Generator
  → Citation Validator
```

### 9.4 权限控制

企业知识库必须在检索阶段而不是生成后做权限过滤：

1. Chunk、实体、关系和社区都绑定租户/部门/ACL；
2. 种子节点召回时先过滤；
3. 图遍历过程中每扩展一个节点都检查权限；
4. 社区摘要不能混入用户无权访问的事实；
5. 日志中避免记录敏感原文。

如果只对最终文本做脱敏，模型在生成过程中已经看到了越权信息。

### 9.5 缓存与性能

常见缓存层：

- 文档解析缓存；
- 实体关系抽取缓存；
- 实体链接缓存；
- Query Rewrite 缓存；
- 社区摘要缓存；
- 热门子图和查询结果缓存；
- Prompt 前缀缓存。

在线延迟优化：

- Local Search 限制最大跳数和候选数；
- 各检索器并行执行；
- 小模型负责路由、抽取和 Rerank，大模型负责最终生成；
- 对图查询设置超时和降级；
- 图检索失败时退化为普通 Hybrid RAG。

## 10. Graph RAG 的评估体系

Graph RAG 不能只评估最终答案，还要分层评估索引、检索和生成。

### 10.1 抽取与图谱质量

| 指标 | 含义 |
| --- | --- |
| Entity Precision / Recall / F1 | 实体抽取准确率、召回率 |
| Relation Precision / Recall / F1 | 关系三元组质量 |
| Entity Linking Accuracy | 实体是否链接到正确规范节点 |
| Duplicate Entity Rate | 重复实体比例 |
| Orphan Node Rate | 没有有效连接的孤立节点比例 |
| Edge Confidence Calibration | 边置信度是否可信 |
| Community Quality | 社区内部紧密度和业务可解释性 |

### 10.2 检索质量

- Recall@K：正确证据是否被召回；
- Precision@K：召回结果中的有效证据比例；
- MRR / NDCG：正确证据的排序质量；
- Path Recall：正确关系路径是否被找到；
- Hop Accuracy：多跳链路的每一跳是否正确；
- Context Relevance：最终上下文与问题的相关性；
- Context Coverage：是否覆盖回答所需的全部信息。

### 10.3 生成质量

- Answer Correctness：答案是否正确；
- Faithfulness / Groundedness：答案是否都能由证据支持；
- Citation Precision / Recall：引用是否准确、是否覆盖关键结论；
- Completeness：复杂问题的各个方面是否回答完整；
- Hallucination Rate：是否生成证据中不存在的事实。

### 10.4 工程指标

- 索引吞吐、索引总成本和增量更新时间；
- P50/P95/P99 查询延迟；
- 单次查询 LLM Token 和费用；
- 图遍历节点数、边数和平均跳数；
- 缓存命中率；
- 降级率、超时率和错误率。

### 10.5 测试集设计

测试集必须覆盖：

1. 单实体事实题；
2. 一跳关系题；
3. 多跳关系题；
4. 跨文档问题；
5. 全局总结题；
6. 时间约束问题；
7. 同名实体消歧题；
8. 无答案问题；
9. 权限隔离问题；
10. 文档更新后的时效性问题。

还应建立普通 RAG、Hybrid RAG 和 Graph RAG 的 A/B 基线，确认图结构带来的质量收益是否值得额外成本。

## 11. Graph RAG 的适用场景与选型

### 11.1 适合使用 Graph RAG

- 企业组织、人脉、股权和供应链关系；
- 金融风控、反欺诈和资金链路；
- 医疗知识、疾病-药物-症状关系；
- 法律案件、法条和引用关系；
- 网络安全攻击路径与威胁情报；
- 科研论文、作者、机构和引用网络；
- 复杂产品依赖、故障传播和根因分析；
- 需要全库主题总结的大规模非结构化知识库。

### 11.2 不一定需要 Graph RAG

- FAQ 和短文档检索；
- 问题通常能由单个 Chunk 回答；
- 数据变化极快，但关系价值不高；
- 数据量小、成本和延迟要求严格；
- 缺少可定义的实体、关系或图结构；
- 普通 Hybrid RAG &#43; Reranker 已达到业务指标。

面试中可以这样回答：

&gt; 我不会因为 Graph RAG 更复杂就默认采用它，而是先用测试集判断问题中多跳、关系和全局查询的占比。如果大多数问题是局部事实，优先使用 Hybrid RAG；只有图结构带来稳定的质量增益，才承担额外的索引和维护成本。

## 12. 高频面试题

### 12.1 Graph RAG 和知识图谱问答有什么区别？

知识图谱问答通常直接把自然语言转换为图查询，主要依赖结构化实体和关系返回精确结果。Graph RAG 的范围更广：它可以同时检索图节点、关系、文本 Chunk 和社区摘要，再由 LLM 综合生成自然语言答案。知识图谱可以是 Graph RAG 的检索底座，但 Graph RAG 还包括非结构化证据、向量检索和生成环节。

### 12.2 Graph RAG 和传统 RAG 的核心区别是什么？

传统 RAG 主要基于 Query 与独立 Chunk 的相似度召回；Graph RAG 显式保存知识之间的连接，并通过邻域、路径或社区进行检索。它更适合多跳关系和全局总结，但索引成本、维护复杂度和查询延迟更高。

### 12.3 为什么不能只把实体关系转成文本后放入向量库？

可以这样做，而且是一个低成本基线。但纯文本向量化会弱化方向、类型、跳数和约束。例如“A 收购 B”和“B 收购 A”可能在向量空间很接近。图结构可以显式执行方向、关系类型、时间和路径条件，并提供稳定的多跳遍历。

### 12.4 为什么使用 Leiden，而不是只用 K-Means？

K-Means 根据向量空间距离聚类，需要预设 K，不能直接利用图的边和拓扑。Leiden 根据图连接优化社区质量，适合发现连接紧密的子图，并能形成层级社区。它与向量聚类解决的问题不同，也可以组合使用。

### 12.5 Local Search 和 Global Search 有什么区别？

Local Search 以 Query 中的具体实体为种子，检索其邻域、关系和原始证据，适合事实与多跳问题。Global Search 检索社区摘要，并对多个社区执行 Map-Reduce，适合主题、趋势和全局总结问题。

### 12.6 图遍历为什么不能无限扩展？

图中可能存在高连接度节点和环。无限扩展会造成候选爆炸、延迟上升和上下文污染。需要通过跳数、关系类型、边置信度、候选数量、Token 预算、时间范围和权限共同限制。

### 12.7 如何处理实体消歧？

先通过名称和别名召回候选实体，再结合实体类型、上下文向量、邻接实体、时间和业务主数据 ID 打分。高置信度自动合并，低置信度保留多个候选或进入人工审核。不能仅依靠字符串完全相等。

### 12.8 如何降低建图时的 LLM 成本？

- 先用规则或 NER 小模型抽实体，再让 LLM 补关系；
- 批量抽取并使用结构化输出；
- 对内容哈希，避免重复抽取；
- 只对高价值文档或候选实体对调用 LLM；
- 使用小模型做抽取，大模型只处理歧义样本；
- 增量更新局部子图；
- 缓存抽取结果和社区摘要。

### 12.9 如何减少图谱中的错误传播？

每条实体和关系都保留 `confidence`、`source_id`、抽取模型版本和原始证据。重要关系要求多源验证或规则校验；低置信边在检索时降权；最终答案必须回到原始 Chunk 验证，不能只根据社区摘要或抽取三元组生成。

### 12.10 Graph RAG 一定比传统 RAG 好吗？

不一定。对于单跳 FAQ，Graph RAG 可能只增加成本和延迟。是否采用取决于查询分布、数据结构、质量增益和成本预算。正确做法是用分类型测试集对比不同方案，而不是只看整体平均分。

### 12.11 图数据库如何选型？

- 原型和小规模实验：NetworkX、igraph；
- 强调 Cypher 生态和开发体验：Neo4j；
- 大规模分布式图：NebulaGraph、JanusGraph 等；
- 已有搜索平台且图需求较轻：可以用 Elasticsearch/OpenSearch &#43; 邻接表；
- 选型要考虑规模、查询模式、写入吞吐、事务、权限、运维和团队经验。

### 12.12 如何支持实时更新？

使用 CDC 或消息队列接收变更，根据稳定文档 ID 找到受影响 Chunk、实体和关系；重新抽取局部内容，更新证据计数和向量；对受影响社区做局部重聚类或标记异步重建；查询时通过版本号或时间戳保证一致性。

### 13.1 参考回答

&gt; 我做的是一个面向长文档复杂问答的轻量 Graph RAG。索引阶段先把 PDF 按约 1200 字符切块并写入 FAISS，再将每个 Chunk 建成图节点。节点的实体由 spaCy 抽取，通用概念由 LLM 结构化抽取；两个 Chunk 的向量相似度超过阈值后，根据语义相似度和共享概念计算边权并建边。
&gt;
&gt; 查询阶段先通过 FAISS 召回 Top-5，并使用 LLM 做上下文压缩，再把候选映射成图的种子节点，通过优先级队列沿高权重边扩展。每轮累计证据后判断是否已经可以完整回答，满足条件就提前终止，否则在预算内继续遍历，最后基于证据生成答案并可视化路径。
&gt;
&gt; 这个实现验证了向量召回与图扩展的互补性，但它仍是文本块图，不是完整的实体关系 GraphRAG。下一步会补充稳定 ID、来源引用、关系类型、上下文预算、近邻建图、Leiden 社区摘要，以及 Local/Global 查询路由。对于大规模场景，我会把 O(N²) 两两建边替换为 ANN Top-K 建边，并把 NetworkX 替换为可持久化图数据库。

## 14. 手写系统设计题答题框架

如果面试官让设计一个企业级 Graph RAG，可以按以下顺序回答：

1. **澄清需求**：数据规模、更新频率、查询类型、延迟、权限、是否要求引用。
2. **确定图模型**：实体图、Chunk 图，或二者结合。
3. **设计索引链路**：解析、切块、抽取、消歧、建图、社区、Embedding、持久化。
4. **设计查询链路**：Query 分析、路由、多路召回、图扩展、融合、Rerank、生成。
5. **控制性能**：ANN 建边、最大跳数、候选上限、缓存、并行和降级。
6. **保证可信**：关系置信度、原始证据、引用校验、无答案处理。
7. **处理更新**：稳定 ID、版本、CDC、局部重建和社区摘要刷新。
8. **保证安全**：索引级和遍历级 ACL、租户隔离、日志脱敏。
9. **建立评估**：按局部、多跳、全局问题分别对比 RAG 基线。
10. **说明权衡**：质量、延迟、成本、复杂度和可维护性。

## 15. 速记总结

```text
Graph RAG = RAG &#43; 显式知识连接

索引：
文档 → 切块 → 实体/关系/概念抽取 → 消歧对齐 → 建图
    → 社区检测 → 社区摘要 → 图索引 &#43; 向量索引

查询：
Query → 分析与路由
      → Local：实体 &#43; 邻域 &#43; 路径
      → Global：社区摘要 &#43; Map-Reduce
      → Hybrid：向量 &#43; BM25 &#43; 图
      → 融合/Rerank → 动态 Prompt → 答案与引用

核心优势：
多跳关系、跨文档连接、全局总结、可解释路径

主要代价：
抽取成本、错误传播、图谱维护、索引复杂度、查询延迟

当前 Notebook：
FAISS &#43; NetworkX &#43; Chunk 节点 &#43; 概念属性 &#43; 加权边 &#43; Dijkstra-like 遍历

当前缺失：
独立实体节点、关系类型、Leiden 社区、社区摘要、Global Search、稳定引用、增量更新
```

最终记住一句话：

&gt; Graph RAG 的关键不是“用了图数据库”，而是把知识之间的结构关系纳入索引、检索、排序和证据组织全过程，并且通过评估证明这些结构确实改善了目标查询。
