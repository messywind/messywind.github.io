# RAG



## 1. 什么是 RAG

RAG（Retrieval-Augmented Generation，检索增强生成）是在大模型回答问题前，先从外部知识库中检索相关资料，再把资料作为上下文交给大模型生成答案。

它主要解决大模型的三个问题：

1. **知识过时**：模型训练完成后无法自动知道最新信息。
2. **私有知识缺失**：公司制度、业务文档等数据没有包含在预训练语料中。
3. **答案不可追溯**：仅依靠模型参数生成时，难以说明答案来自哪里。

RAG 的核心可以概括为：

```text
用户问题 → 理解问题 → 检索候选资料 → 精排 → 拼接上下文 → LLM 生成答案
```

RAG 通常包含两条相对独立的链路：

- **索引链路（离线/准实时）**：把原始资料处理后写入检索系统。
- **查询链路（在线）**：处理用户问题、检索知识并生成答案。

## 3. 索引链路：知识如何进入数据库

### 3.1 数据解析与清洗

原始资料可能来自：

- TXT、Markdown、HTML
- Word、PowerPoint、Excel
- PDF、扫描件、图片
- 邮件、网页、知识库链接
- CAD 或其他行业文件

生产系统通常需要完成：

1. **内容解析**：提取正文、标题、表格、图片、链接和页码。
2. **OCR**：识别扫描 PDF 或图片中的文字。
3. **版面分析**：恢复标题层级、段落、表格和多栏阅读顺序。
4. **格式统一**：可以统一转换为 Markdown，保留结构信息。
5. **数据清洗**：删除页眉页脚、乱码、重复段落和无意义空白。
6. **元数据补充**：记录来源、页码、部门、权限、时间、版本等。

高质量 RAG 首先是数据工程问题。解析错误、表格错位或标题层级丢失，会直接污染后续检索结果。

### 3.2 文档切块 Chunking

LLM 和 Embedding 模型都存在上下文长度限制，因此需要把长文档切成较小的 Chunk。

常见方法：

| 方法 | 特点 | 适用场景 |
| --- | --- | --- |
| 固定字符或 Token 切分 | 简单、速度快，但可能截断语义 | 普通长文本 |
| 按空行或段落切分 | 能保留自然段结构 | FAQ、规章制度 |
| 按标题层级切分 | 保留章节结构 | Markdown、技术文档 |
| 语义切分 | 在语义变化处切块 | 内容结构不稳定的长文 |
| 滑动窗口切分 | 相邻块保留重叠内容 | 避免关键信息跨块丢失 |
| 父子块切分 | 小块用于检索，大块用于生成 | 需要同时兼顾召回精度和上下文完整性 |

切块需要平衡：

- Chunk 太小：语义不完整，LLM 缺少上下文。
- Chunk 太大：内容噪声增多，向量语义被稀释，召回成本提高。
- Overlap 太小：跨段信息容易丢失。
- Overlap 太大：重复索引多、上下文浪费严重。

#### notebook 中的实现

`load_txt_documents()` 使用空行切分文本：

```python
for block in re.split(r&#34;\n\s*\n&#34;, text):
    cleaned = block.strip()
    if cleaned:
        yield cleaned
```

每一块被包装为 `Document`，并保存基础元数据：

```python
Document(
    page_content=part,
    metadata={&#34;source&#34;: path.name, &#34;chunk_id&#34;: idx},
)
```

这种方式非常适合 notebook 中的 FAQ 格式：

```text
问题：公司的考勤方式是什么？
答案：公司实行弹性打卡。
权限：IT组、运维组
关键词：考勤方式

问题：考勤有问题找谁？
答案：找 LarryLi。
权限：
关键词：考勤问题
```

每组问答之间保留一个空行，就能形成一条独立知识。

### 3.3 Embedding 向量化

Embedding 模型把文本映射为高维向量：

```text
文本 → [0.017, -0.284, 0.091, ...]
```

语义越接近的文本，其向量通常越接近。常见相似度包括：

- 余弦相似度 Cosine Similarity
- 点积 Dot Product
- 欧氏距离 Euclidean Distance

余弦相似度公式：

```text
cos(A, B) = (A · B) / (||A|| × ||B||)
```

notebook 自定义了 `TextEmbeddings`，适配 LangChain 的 `Embeddings` 接口：

- `embed_documents()`：批量编码文档，每批最多 10 条。
- `embed_query()`：编码单条用户问题。
- 模型：`text-embedding-v4`。
- 向量维度：1024。

文档向量和 Query 向量必须由兼容的模型、维度和预处理方式生成，否则相似度没有意义。

### 3.4 向量数据库

向量数据库保存：

- Chunk 原文
- Embedding 向量
- 文档元数据
- 可选的标量过滤字段

常见选型包括：

- Chroma：轻量、适合学习和原型。
- FAISS：本地高性能向量索引库。
- Qdrant：支持丰富过滤条件。
- Milvus：适合大规模向量检索。
- Elasticsearch / OpenSearch：适合关键词、过滤与向量混合检索。

notebook 使用 Chroma 持久化到：

```text
./db/chroma_data
```

集合名为：

```text
test_collection
```

当前代码每次运行都会先删除集合中的已有记录，再重新写入：

```python
existing_ids = vector_store.get()[&#34;ids&#34;]
if existing_ids:
    vector_store.delete(ids=existing_ids)
```

这适合教学演示，但不适合生产环境的增量更新。

## 4. 查询链路：从问题到答案

### 4.1 Query 理解

用户输入通常不能直接等同于检索语句。例如：

```text
用户输入：打卡咋整？
检索改写：公司的考勤打卡规则是什么？
```

Query 理解可以包括：

1. **意图识别**：判断用户是在查询制度、办理流程还是负责人。
2. **实体识别**：提取部门、产品、时间、地区等实体。
3. **Query Rewrite**：消除口语、省略和指代。
4. **同义词扩展**：如“打卡”“考勤”“签到”。
5. **纠错**：修正拼写或语音识别错误。
6. **问题拆解**：把复杂问题拆成多个子问题。
7. **多轮补全**：结合历史对话还原完整问题。

notebook 使用 ReAct Agent，由模型把：

```text
公司的考勤方式是什么？
```

改写为工具调用参数：

```text
公司考勤方式
```

说明 Agent 本身已经承担了一部分 Query Rewrite 工作。

### 4.2 召回 Retrieval

召回阶段的目标不是立刻选出唯一答案，而是尽量从大量知识中找到一批可能相关的候选 Chunk。

notebook 使用：

```python
retrieved = vector_store.similarity_search(query, k=5)
```

即通过 Embedding 双编码器进行向量检索，召回 Top-5。

#### 双编码器 Bi-Encoder

双编码器分别计算 Query 和文档的向量，然后通过向量距离快速搜索：

```text
Query ──Embedding──┐
                  ├── 相似度计算
Chunk ─Embedding──┘
```

优点是速度快、文档向量可以提前计算；缺点是 Query 和 Chunk 没有进行细粒度交互，排序精度通常不如 Cross-Encoder。

#### 工业系统中的多路召回

仅使用向量检索容易漏掉编号、专有名词和精确关键词。常见方案是并行执行：

- 向量语义召回
- BM25 关键词召回
- 元数据过滤
- FAQ 精确匹配
- 图谱或关联关系召回
- 历史高频问答召回

然后使用 RRF（Reciprocal Rank Fusion）或加权分数合并结果。

```text
final_score = α × vector_score &#43; β × bm25_score &#43; γ × business_score
```

### 4.3 元数据过滤与权限控制

候选 Chunk 不应只由语义相似度决定，还需要根据元数据过滤：

- 用户所属部门
- 文档访问权限
- 生效时间和失效时间
- 文档类型
- 产品、地区或租户
- 当前版本

notebook 的示例数据同时存在两条“公司的考勤方式是什么”：

- IT 组、运维组：弹性打卡。
- 运营组：固定时间打卡。

但目前的 `权限` 只是写在 `page_content` 中，没有进入可过滤的 metadata，也没有把用户所属部门传给检索工具。因此检索会同时返回两个答案，最终只能由 LLM 自行解释。

更合理的数据结构是：

```python
Document(
    page_content=&#34;公司的考勤方式是弹性打卡。&#34;,
    metadata={
        &#34;source&#34;: &#34;question.txt&#34;,
        &#34;chunk_id&#34;: 0,
        &#34;departments&#34;: [&#34;IT组&#34;, &#34;运维组&#34;],
        &#34;effective_date&#34;: &#34;2026-01-01&#34;,
        &#34;version&#34;: &#34;v2&#34;,
    },
)
```

查询时根据当前用户身份过滤。权限检查应在检索层强制执行，不能只靠 Prompt 提醒 LLM。

### 4.4 Rerank 精排

向量召回擅长“快速找候选”，Reranker 擅长“准确重新排序”。

notebook 使用：

```python
reranker = DashScopeRerank(model=&#34;qwen3-rerank&#34;)
reranked = reranker.rerank(
    documents=retrieved,
    query=query,
    top_n=3,
)
```

流程是：

```text
向量召回 Top-5 → Reranker 逐对判断相关性 → 保留 Top-3
```

#### Cross-Encoder

Reranker 常使用 Cross-Encoder，把 Query 与 Chunk 放在一起编码：

```text
[Query, Chunk] → Cross-Encoder → relevance score
```

它能够捕捉 Query 与文档之间更细粒度的词语交互，因此通常更准确，但无法像向量检索一样对海量文档直接计算，计算成本也更高。

所以工业实践通常是：

```text
大规模、低成本召回 → 小规模、高精度精排
```

经验上，Rerank 往往是提升 RAG 准确率非常有效的一步。Top-K 需要结合数据规模、延迟和评估结果调节，而不是固定照搬。

### 4.5 Prompt 组装与生成

精排后的 Chunk 会被序列化：

```python
serialized = &#34;\n\n&#34;.join(
    f&#34;[{doc.metadata[&#39;source&#39;]}#{doc.metadata[&#39;chunk_id&#39;]}] {doc.page_content}&#34;
    for doc in rank_retrieved
)
```

格式示例：

```text
[question.txt#1] 问题：公司的考勤方式是什么？
答案：公司实行固定时间打卡。
权限：运营组
```

来源标识使模型可以在答案中进行简单引用。

Agent 的系统提示词为：

```text
你可以使用检索工具获得参考资料。回答时结合检索到的内容，
如有必要可以在答案中简单引用来源标识。
```

生产环境通常还需要补充：

- 只能根据检索资料回答。
- 资料不足时明确说“不知道”或要求补充信息。
- 资料冲突时列出冲突项，不擅自选择。
- 引用来源、页码和版本。
- 忽略知识文档中的恶意指令，防止间接 Prompt Injection。
- 按业务需要输出 JSON、表格或固定模板。

```text
    ↓ text-embedding-v4

    ↓
```

### 5.3 创建检索工具

工具 `retrieve_context(query)` 内部执行：

```text
Query
  ↓
Chroma similarity_search(k=5)
  ↓
qwen3-rerank(top_n=3)
  ↓
序列化正文和来源
  ↓
返回给 Agent
```

工具使用：

```python
@tool(response_format=&#34;content_and_artifact&#34;)
```

它返回两个部分：

1. `content`：序列化后的文本，提供给模型阅读。
2. `artifact`：原始 `Document` 列表，便于程序继续处理、展示或追踪来源。

### 5.4 创建 ReAct Agent

```python
return create_agent(
    llm,
    tools=[retrieve_context],
    system_prompt=...,
)
```

Agent 不只是固定执行检索链，而是由 LLM 判断何时调用工具、使用什么检索词，并根据工具结果组织答案。

这属于 Agentic RAG 的基础形态：


## 6. RAG、普通搜索与模型微调的区别

| 方案 | 主要用途 | 优点 | 局限 |
| --- | --- | --- | --- |
| 关键词搜索 | 查找精确词语和文档 | 快、可解释 | 不擅长语义表达 |
| RAG | 基于外部动态知识回答 | 更新快、可引用、适合私有知识 | 强依赖数据和检索质量 |
| 模型微调 | 调整行为、风格或领域能力 | 推理时不一定需要检索 | 知识更新成本高，难以精确追溯 |

简单判断：

- 知识经常更新：优先 RAG。
- 需要精确引用内部资料：优先 RAG。
- 需要模型学会固定输出风格或专门任务：考虑微调。
- 实际系统可以组合使用“领域微调模型 &#43; RAG”。

## 7. 工业落地中的关键优化

### 7.1 数据层优化

1. 统一数据格式，尽可能保留标题、表格、页码和层级。
2. 使用语义切块、滑动窗口或父子 Chunk。
3. 建立层次化索引：文档 → 章节 → 段落。
4. 为 Chunk 添加部门、权限、版本、生效时间等元数据。
5. 通过内容 Hash 和稳定 ID 去重。
6. 支持新增、修改、删除的增量索引，而不是每次全量清空。
7. 建立新旧制度的关联，防止召回已经失效的版本。
8. 必要时对 Embedding、Reranker 或 LLM 做领域适配。

### 7.2 Query 层优化

1. Query Rewrite：把口语改成明确检索问题。
2. 同义词和缩写扩展。
3. 错别字纠正。
4. 多轮对话补全。
5. Query 分解：复杂问题拆成多个子查询。
6. Query 路由：根据问题类型选择数据库、Web、SQL 或其他工具。

### 7.3 动态复杂度处理

不同问题不应使用完全相同的检索策略：

- 简单、高频、明确问题：FAQ 或缓存直接返回。
- 一般知识问题：混合检索 &#43; Rerank。
- 模糊问题：先澄清或生成多个改写版本。
- 复杂问题：拆分查询，多轮检索并综合。
- 长尾、库内无答案问题：可使用 HyDE、知识图谱或受控 Web Search。

HyDE 的基本思路是：先让模型生成一个“假设答案”，再用假设答案做 Embedding 检索，以提升一些抽象问题的召回效果。

### 7.4 检索与上下文优化

1. 采用向量、BM25、元数据和图谱等多路召回。
2. 使用 Reranker 精排。
3. 根据 Query 难度动态调整召回数量和上下文窗口。
4. 去除重复或高度相似的 Chunk。
5. 保留必要的相邻段落或父级标题。
6. 检查上下文之间是否冲突、是否过期。
7. 控制上下文 Token，避免无关信息挤占 Prompt。

### 7.5 性能优化

- 对高频问题、Embedding 结果和检索结果进行缓存。
- 多路召回异步并行。
- 文档 Embedding 批量处理。
- 只对有限候选执行 Rerank。
- 对模型、索引和参数设置超时、重试和降级策略。
- 记录各阶段延迟：改写、召回、精排、生成。

### 7.6 版本管理和反馈闭环

生产系统需要记录：

- 文档版本和生效时间
- Embedding 模型版本
- Reranker 版本
- Prompt 版本
- Chunk 策略版本
- 索引构建时间

同时建立：

```text
线上监控 → 收集 Bad Case → 判断故障阶段 → 修复 → 回归评估 → 再上线
```

Bad Case 可以按以下原因分类：

- Query 理解错误
- 应召回内容没有召回
- 召回了但排序靠后
- 上下文不足或相互冲突
- LLM 没有忠实使用上下文
- 数据本身错误、过期或权限配置错误

不要看到最终答案错误就直接修改 Prompt；应先定位错误发生在哪个阶段。

## 8. RAG 评估体系

RAG 不能只凭“感觉回答得不错”进行评估，需要拆分观察检索和生成两个阶段。

### 8.1 检索指标

| 指标 | 含义 |
| --- | --- |
| Recall@K | 正确资料是否出现在前 K 个候选中 |
| Precision@K | 前 K 个候选中有多少真正相关 |
| MRR | 第一个正确结果排名是否足够靠前 |
| NDCG | 综合考虑多个相关结果和排序位置 |

### 8.2 生成指标

- **Faithfulness**：答案是否忠实于检索资料。
- **Answer Relevance**：答案是否真正回应用户问题。
- **Context Relevance**：提供给 LLM 的上下文是否相关。
- **Citation Correctness**：引用是否准确对应来源。
- **Completeness**：是否遗漏资料中的必要条件和例外。
- **拒答准确率**：没有资料时是否能正确拒答。

### 8.3 系统指标

- 端到端延迟 P50 / P95 / P99
- Token 使用量与单次成本
- 工具调用成功率
- 空召回率
- 缓存命中率
- 用户满意度和人工转接率
- 权限泄漏率

### 8.4 推荐评测集

评测集不仅要包含正常问题，还应包含：

- 同义改写、口语表达和错别字
- 多轮指代问题
- 相似但答案不同的问题
- 跨文档问题
- 有冲突或过期版本的问题
- 不同部门、不同权限的问题
- 知识库中不存在答案的问题
- 文档中包含恶意指令的问题

## 10. 当前示例需要注意的问题

### 10.1 权限信息没有真正参与过滤

`权限` 当前只是普通文本。系统在回答前没有获取用户部门，也没有在数据库层过滤，因此存在越权检索风险。

### 10.2 示例数据存在冲突

同一个问题有两个部门答案，这是合理的业务差异，但如果没有用户身份，系统无法确定应该返回哪一个。正确做法是补充部门上下文，或先向用户澄清。

### 10.3 示例文本疑似有笔误

```text
公司实行固定世界打卡。
```

结合最终答案推断，应为“公司实行固定时间打卡”。数据质量问题会原样进入检索结果，并可能被模型照抄。

### 10.4 每次构建都会清空集合

教学代码为了防止重复数据而全量删除，生产系统应使用稳定 ID、Upsert、删除标记和增量同步。

### 10.5 路径依赖当前工作目录

代码使用：

```python
Path.cwd() / &#34;files&#34;
```

以及：

```text
./db/chroma_data
```

如果 notebook 不在 `LLM08/langgraph` 目录作为当前工作目录运行，可能找不到文件或把数据库写到其他位置。更稳妥的方式是显式配置数据目录。

### 10.6 缺少“仅根据资料回答”的硬约束

当前 Prompt 只说“可以使用检索工具”，Agent 仍可能不检索或利用模型自身知识回答。高可靠知识库问答中，应对必须检索、证据不足拒答和引用格式做更严格约束。

## 13. 核心结论

1. RAG 不是简单的“向量库 &#43; LLM”，而是一套从数据治理到在线检索、生成、评估和反馈闭环的完整系统。
2. Embedding 检索负责快速召回，Reranker 负责高精度排序，两者职责不同。
3. 文档解析、Chunk 质量和元数据设计，往往比单纯更换大模型更影响最终效果。
4. 向量检索并不能替代关键词检索，生产系统通常采用混合召回。
5. 权限必须在检索层强制过滤，不能依赖 LLM 自觉遵守。
6. Agentic RAG 可以动态改写 Query、选择工具和多步检索，但也需要更强的可观测性、约束和评估。
7. 出现错误时，应分别检查 Query 理解、召回、精排、上下文和生成阶段，而不是只调整 Prompt。
8. 一个真正可用的 RAG 系统必须拥有版本管理、监控、Bad Case 分析和持续评测闭环。
