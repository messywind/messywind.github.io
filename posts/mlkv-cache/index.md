# KV Cache


## 一、 为什么我们需要 KV Cache？（痛点与原理）

### 1. 灾难现场：自回归的重复计算

在 Decoder-only 架构（如 GPT, LLaMA）的推理阶段，文本生成是自回归（Autoregressive）的——必须摸着石头过河，一个词一个词往外蹦。

* 如果没有缓存，当模型预测第 $N&#43;1$ 个词时，它需要把前面 $N$ 个词作为一个整体，重新走一遍几百层的矩阵乘法。
* 这种“每次都从头算一遍历史特征”的方式，会导致时间复杂度随生成长度呈平方级（$O(N^2)$）暴增。

### 2. 核心原理：到底存了什么？

在自注意力公式 $\text{Attention}(Q, K, V) = \text{Softmax}(\frac{Q K^T}{\sqrt{d_k}}) V$ 中：

* 历史 Token 的 $K$（键）和 $V$（值）在未来的生成中**永远不会改变**。
* 当前正在生成的新词，只需要它自己的 $Q_{new}$ 去和历史的 $K_{cache}$ 算匹配度，再加权 $V_{cache}$ 即可。
* **结论**：我们在显存中开辟一块空间，只把每一层算好的历史 $K$ 和 $V$ 张量存下来，这就是 **KV Cache**。

### 3. 推理的两阶段生命周期

1. **Prefill（预填充阶段）**：一次性读入超长 Prompt，算力拉满，把所有 Prompt 词的 $K, V$ 塞进缓存。预测出第 1 个新词。（计算密集型）
2. **Decode（解码阶段）**：每次只输入 1 个新词，算出它的 $q, k, v$。从显存中读出历史 KV，把新的 $k, v$ 拼接到末尾，算出下一个词。（访存密集型）

---

## 二、 致命危机：KV Cache 带来的“显存墙”

KV Cache 本质上是极端的“空间换时间”。
以 LLaMA-2-7B (FP16精度) 为例，存 1 个 Token 的 KV Cache 需要：
`32层 × 4096维 × 2(K和V) × 2字节 = 512 KB`。
如果并发服务 100 个用户，每人 4000 上下文，仅缓存就会吃掉 **200 GB 显存**！这逼迫工业界衍生出了两大维度的压缩方案：**架构级压缩（GQA）** 与 **策略级压缩（StreamingLLM）**。

---

## 三、 架构级压缩：从 MHA 到 GQA

为了从物理维度缩小 KV Cache 的体积，模型的 Attention 架构经历了三次演进：

1. **MHA (多头注意力 - 基准)**：
* $Q, K, V$ 头数一样多（例如都是 32 个头，按 32 份切割）。显存占用 100%，生成质量最高。


2. **MQA (多查询注意力 - 极端压缩)**：
* 32 个 $Q$ 头，但**全局共享 1 个 $K$ 头和 1 个 $V$ 头**。显存占用直降至约 3.1%，但模型表达能力严重受损，生成变傻。


3. **GQA (分组查询注意力 - 完美折中)**：
* **原理**：将 32 个 $Q$ 头分成 8 组。每组的 4 个 $Q$ 头共享 1 个 $K$ 头和 1 个 $V$ 头。
* **代码维度机制**：并不是生成高维后再切分。$K$ 和 $V$ 映射时直接生成较小的维度（8个头），然后在做矩阵乘法的那一瞬间，底层通过广播机制（Broadcast）将 $K$ 和 $V$ 在头的维度上复制 4 份，对齐 $Q$ 的 32 个头。
* **收益**：显存砍掉 75%，但推理质量几乎与标准 MHA 持平（LLaMA-2/3 标配）。

## 四、 策略级压缩 (KV Cache Compression)：长文本驱逐与保留策略

即便用了 GQA，当用户输入极其恐怖的超长文本（如十万字小说、无限轮对话）时，显存依然会爆。此时需要做 **Token Eviction（Token 驱逐/丢弃）**：决定删掉哪些历史缓存。

### 1. 常规策略的失败（滑动窗口的困境）

* **Dense Attention**：全量保留。最终必定导致 OOM（显存溢出）。
* **Window Attention（滑动窗口）**：只保留最近的 $N$ 个 Token。
* **致命现象**：一旦最开头的几个 Token 滑出窗口被删掉，模型会瞬间崩溃，胡言乱语（Perplexity 飙升）。



### 2. 核心大发现：“注意力水槽 (Attention Sinks)”

为什么删掉开头的几句废话，模型就崩溃了？

* **底层数学逻辑**：Self-Attention 里的 `Softmax` 函数要求所有词的注意力权重之和必须等于 1。
* **水槽效应**：当模型在生成某个词时，如果它觉得前面没有任何一个词特别重要，它为了凑够 Softmax 的“1”，会习惯性地把大量无用的注意力权重**倾倒在全句最开头的 1~4 个 Token（如起始符 `&lt;s&gt;`）上**。
* **真相**：开头的 Token 本质上充当了“垃圾桶 / 稳定器”。如果把它们删了，无处安放的权重会导致 Softmax 分布大乱，底层特征全盘错位。

### 3. 终极解法：StreamingLLM (流式长文本优化)

基于 Attention Sinks 的发现，工业界提出了一种极度简单却极其强悍的 KV Cache 压缩分离策略，它的缓存池被严格划分为两部分：

1. **Attention Sink Cache（定海神针）**：
* **死死锁住**序列最开头的 4 个 Token 的 KV Cache，**永远不驱逐**。它们负责承接多余的注意力分数，维持 Softmax 分布的绝对稳定。


2. **Local Cache（局部语义）**：
* 设定一个固定大小的滑动窗口（例如最近的 1024 个词），只保留最近生成的 Token 以提供正常的上下文连贯性。


3. **无情抛弃中间层**：
* 除了“开头 4 个”和“最近 1024 个”，这中间的所有几万、几十万字的历史文本，一旦滑出窗口，立刻从显存中清空丢弃。



**💡 策略级压缩总结：**
通过这种 KV Cache 压缩策略，大模型可以用 $O(1)$ 的极小且固定的显存，实现**无限长度的流式对话**，永远不爆显存，且生成质量绝不崩溃。

太有眼光了！你点名的这两个算法（**H2O** 和 **Quest**）都是近两年大模型长文本推理优化领域非常前沿且硬核的工作。

如果说前文提到的 `StreamingLLM` 是一种“静态、一刀切”的压缩策略，那么 `H2O` 和 `Quest` 则代表了目前工业界最高阶的“动态感知（Query-Aware / Data-Driven）”优化流派。

我们可以把这两个技术完美地补充到“KV Cache 笔记”的进阶部分。一个解决的是“该扔谁、留谁（Eviction）”**，另一个解决的是**“该读谁（Loading）”。

## 五、 进阶策略级压缩：动态感知与精准打击（H2O 与 Quest）

在长文本大模型推理中，我们不仅面临显存容量不够的“空间问题”，还面临显存读写速度太慢的“访存带宽问题”。为了解决这两个痛点，学术界提出了比 StreamingLLM 更智能的算法。

### 1. H2O (Heavy-Hitter Oracle) —— 智能驱逐策略（解决“存不下”）

**【痛点】：StreamingLLM 的盲区**
前面提到，StreamingLLM 的策略极其粗暴：只保留【开头 4 个词】和【最近的 1024 个词】，中间的全部无情删掉。
但如果这是一篇十万字的侦探小说，凶手的名字正好出现在第 5000 字（中间层），那 StreamingLLM 早就把它删了，模型最后根本破不了案。

**【H2O 的核心理念：Heavy Hitters（重磅词/高频词）】**
H2O 的作者发现，除了开头的 Attention Sinks，句子中间其实也隐藏着一些极其关键的词（比如文眼、核心实体）。这些词有一个共同特征：**在模型自回归生成的过程中，它们会被后续的词反复、持续地分配极高的注意力分数。**
作者将这些吸分能力极强的 Token 称为 **Heavy Hitters（重磅词）**。

**【H2O 的具体机制（动态记账法）】**

1. **累积记账**：H2O 会为 KV Cache 中的每一个 Token 设立一个“积分账户”。每次生成新词计算 Attention 时，它都会把历史词得到的注意力得分累加到它们的账户上。
2. **末位淘汰（Eviction）**：当 KV Cache 达到显存设定的上限（比如 2048 个槽位）时，H2O 不会像滑动窗口那样盲目删最老的词。它会去查看积分榜，**无情删掉那些“累积得分最低”的 Token**。
3. **保留精英**：最终留在 KV Cache 里的，除了最近的 Local Token 之外，全是各个位置上的 Heavy Hitters（重磅词）。

*💡 一句话总结 H2O：通过动态追踪注意力得分，精准保留中间段落里的“核心关键词”，实现了比静态窗口强得多的上下文理解能力。*

---

### 2. Quest (Query-Aware Sparsity) —— 智能加载策略（解决“读太慢”）

**【痛点】：Memory Wall（显存墙与访存瓶颈）**
在 Decode（解码）阶段，每生成一个新词，无论如何压缩，GPU 都必须把显存里剩下的所有 KV Cache **全部搬运到计算单元（SRAM）里**去和当前的 Query 做点积。
这种“每次都全盘读取”的行为极其消耗显卡带宽，导致大模型推理速度慢得像牛车（这就是典型的 Memory-bound）。但实际上，对于当前正在生成的这个词，历史的 KV Cache 里只有极小一部分是对它有用的。

**【Quest 的核心理念：KV Cache Loading（带索引的按需加载）】**
既然不是每个历史块都有用，那我能不能**先快速猜一下谁有用，然后只加载有用的部分**？Quest 就是为 KV Cache 引入了类似数据库“建立轻量级索引”的机制。

**【Quest 的具体过程（两阶段过滤机制）】**
Quest 把长长的 KV Cache 像操作系统的内存一样，切分成很多个**页（Pages / Blocks）**，每页比如存 16 个 Token。

* **阶段一：建立轻量级索引（建目录）**
在算好的每个 KV Page 上，Quest 并不需要读取整个庞大的矩阵，而是只记录这个 Page 里特征维度的**最大值和最小值（Min-Max bounds）**。这相当于给这一页数据贴了一个仅仅几个字节的微型“标签”。
* **阶段二：粗筛（Rough Filtering）**
当新词的 Query 生成后，Quest 先不碰庞大的真实 KV Cache，而是让 Query 先去和那些微型的“页标签（Min-Max）”快速算一个极其廉价的近似得分。
* **阶段三：按需加载并精算（Exact Compute）**
通过粗筛，Quest 选出了得分最高的 Top-K 个 Page（比如只占总大小的 10%）。此时，GPU **只把这 10% 真正有用的 KV 矩阵从显存（HBM）中物理加载出来**，进行最终精确的 Attention 点积计算。

*💡 一句话总结 Quest：它通过给 KV Cache 分块并建立微型标签，在新 Query 到来时先“看标签选人”，只把高度匹配的 KV 块从显存搬到计算单元，极大地打破了长文本推理的带宽瓶颈。*

### 📝 终极对比总结

如果你在面试中能同时祭出这两个技术，绝对能秒杀绝大多数候选人：

| 算法 | 优化维度 | 解决的核心问题 | 底层核心机制 |
| --- | --- | --- | --- |
| **GQA** | 架构级 | 模型参数过大、显存占用过高 | 让多个 Q 头物理共享同一份 K 和 V。 |
| **StreamingLLM** | 策略级 (Eviction) | 轮数无限导致必爆显存 | 永远锁定开头 4 个词（Sinks）&#43; 最近滑动窗口。 |
| **H2O** | 策略级 (Eviction) | 静态窗口丢失核心实体 | 动态记录累积注意力得分，只保留高分重磅词。 |
| **Quest** | 访存级 (Loading) | Decode 阶段搬运 KV 太慢 | 建立 Page 级轻量索引，Query 感知，按需读取显存。 |

* **H2O** 决定了你的显存里**存什么**才能让模型不忘掉关键信息；
* **Quest** 决定了你的显卡**怎么读**才能让生成速度起飞。
