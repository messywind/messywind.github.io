## 一、如何优化 RAG 全链路耗时？

### 1. 面试回答主线

优化 RAG 延迟时，我不会一上来就替换模型，而是先对全链路做 tracing 和 profiling，将总耗时拆开：

```text
总耗时 = 查询处理 &#43; Query Embedding &#43; 检索 &#43; 重排
       &#43; Prompt 构造 &#43; LLM 首 Token &#43; LLM 解码 &#43; 网络与排队耗时
```

重点同时观察：

- **端到端延迟**：P50、P95、P99，而不只是平均值。
- **TTFT**：Time To First Token，首 Token 延迟。
- **TPOT**：Time Per Output Token，后续每个 Token 的生成耗时。
- **吞吐量**：QPS、并发数、Token/s。
- **效果与成本**：优化不能明显损害召回率、答案质量，或造成不可接受的成本增长。

然后针对耗时占比最大的阶段优化，并通过 A/B 测试验证效果。

### 2. Query Embedding 优化

- 选择效果满足要求的更小 Embedding 模型，避免盲目使用大模型。
- 使用 GPU、ONNX Runtime、TensorRT 等进行推理加速；服务化时可使用动态批处理。
- 对模型进行 FP16、BF16 或 INT8 量化，但要重新验证召回效果。
- 缓存高频查询及归一化后查询的 Embedding。
- 对批量离线任务进行 batch 推理，提高设备利用率。
- 文档 Embedding 应在离线摄取阶段预计算，在线链路只计算 Query Embedding。

&gt; 注意：在线请求量较低时，强行等待 batch 可能增加单请求延迟，需要在吞吐量和延迟之间权衡。

### 3. 召回阶段优化

#### 向量索引

- 根据数据规模和精度要求选择索引，例如 HNSW、IVF、IVF-PQ。
- 调整 HNSW 的 `efSearch`、IVF 的 `nprobe` 等参数，在召回率和耗时之间取平衡。
- 对超大规模知识库进行合理分片和并行检索。
- 将高频索引或热点数据放在内存中，减少磁盘 I/O。
- 避免频繁重建整个索引，采用增量更新或分层索引。

#### 缩小搜索空间

- 利用租户、时间、文档类型、部门、权限等元数据进行过滤。
- 在数据库支持的情况下优先采用高效的 pre-filter；如果是 post-filter，要警惕过滤后候选不足。
- 按业务域路由到对应知识库，避免所有查询都搜索全库。
- 控制召回数量 `top_k`，不要为了“保险”无限增大候选集。

#### 检索策略

- 语义检索与 BM25 混合检索可以提高鲁棒性，但会增加链路开销，应按场景启用。
- 多路召回尽量并行执行，再通过 RRF 等方式融合结果。
- 查询改写、HyDE、多查询扩展等策略不一定每次都开启，可通过意图分类或难度判断按需触发。

### 4. 重排阶段优化

- 减少送入重排模型的候选数量，例如先召回 50 条，再轻量过滤到 20 条后重排。
- 使用效果足够的轻量 Cross-Encoder 或蒸馏模型。
- 对候选进行 batch 推理，并使用 GPU、ONNX 或 TensorRT 加速。
- 使用级联重排：规则或轻量模型粗排，复杂模型只处理少量高质量候选。
- 对高频问题的召回、重排结果进行缓存。
- 设置相关性阈值，避免把明显无关的片段送入 LLM。

还可以将与查询无关的静态特征提前离线计算，例如来源权威性、内容质量、时效性和业务优先级；在线阶段再与相关性分数融合：

```text
final_score = α × relevance &#43; β × authority &#43; γ × freshness
```

权重不应直接照搬固定比例，而应在标注集上调参，并关注不同分数的量纲归一化。对于高频或复杂问题，也可以预先计算候选集合或预排序结果，降低在线计算量。

### 5. LLM 生成阶段优化

- 减少无效上下文，只保留相关、互补、去重后的片段。
- 控制输入上下文长度和最大输出长度，因为上下文越长，Prefill 成本越高。
- 使用更小或更快的生成模型；简单问题可以路由到小模型，复杂问题再使用大模型。
- 使用量化、连续批处理、Paged Attention、推测解码等推理优化。
- 对固定系统提示词或公共前缀使用 Prefix Cache/KV Cache。
- 缓存高频且时效要求不高的答案，并设计知识版本号与过期策略。
- 使用流式输出降低用户感知延迟。需要注意，Streaming 主要改善 TTFT 和交互体验，不一定降低总生成时间。

### 6. 架构与工程优化

- 将可并行的环节并行执行，例如多路召回、权限检查、问题分类。
- 避免不必要的串行调用和重复 RPC；使用连接池、长连接，并减少跨地域网络通信。
- 将 Embedding、向量库、重排和 LLM 服务部署在网络距离较近的位置。
- 使用异步 I/O，合理设置超时、重试、熔断和降级策略。
- 对热点数据、检索结果、Prompt 前缀和最终答案进行分层缓存。
- 处理排队问题：扩缩容、限流、负载均衡，并减少长尾请求。
- 预计算高频问题、文档摘要、章节标题、实体与关键词等辅助索引。

### 7. 一个较完整的口述答案

&gt; 我会先用 tracing 将 RAG 延迟拆成 Embedding、召回、重排、Prompt 构造、LLM Prefill 和 Decode，并观察 P50、P95、P99，而不是凭感觉优化。Embedding 可以通过小模型、量化、GPU 推理和缓存优化；召回阶段可以调整 HNSW 或 IVF 参数、使用元数据过滤、控制 top-k 和缓存热点结果；重排阶段可以减少候选集、采用轻量模型与 batch 推理；生成阶段重点减少无效上下文、使用模型路由、Prefix Cache、推测解码和流式输出。架构上还可以并行多路召回、减少 RPC、缓存热点数据。最后必须用 A/B 测试同时验证延迟、召回率、答案质量和成本，防止为了快而牺牲效果。

### 8. 常见追问

#### top-k 越小越好吗？

不是。`top_k` 太大会增加重排、Prompt 和 LLM Prefill 耗时，还可能引入噪声；太小则可能漏掉正确证据。应通过验证集绘制 `top_k—Recall—延迟—成本` 曲线后选择。

#### 缓存应该缓存什么？

- Query Embedding。
- 标准化查询对应的检索结果。
- 重排结果。
- 固定 Prompt 的前缀 KV。
- 高频问答结果。

缓存键中通常需要包含租户、用户权限、知识库版本、模型版本和检索参数，避免越权或旧数据污染。

#### Streaming 是否真的优化了耗时？

Streaming 主要降低用户感知到的首 Token 延迟，并不会必然减少完整答案的生成耗时。

## 二、RAG 中 PDF 解析与滑窗切分有什么问题？

### 1. PDF 解析的根本难点

PDF 更接近一种“页面绘制格式”，保存的是字符和元素在页面上的坐标，不一定保存自然的阅读顺序和语义结构。因此，直接抽取文字再按固定长度滑窗，容易丢失文档结构。

### 2. 常见问题

#### 文本与版面问题

- 双栏、多栏文档的文字顺序错乱。
- 页眉、页脚、页码被重复提取，形成大量噪声。
- 标题、正文、列表、脚注之间的层级关系丢失。
- 字符编码或字体映射异常，出现乱码、缺字。
- 跨页段落被错误拆开。

#### 表格、公式和图片问题

- 表格按纯文本提取后，行列关系丢失。
- 合并单元格、跨页表格和复杂边框难以还原。
- 数学公式、上下标和特殊符号解析错误。
- 扫描版 PDF 没有文本层，必须进行 OCR。
- 图片、流程图中的关键信息无法由普通文本解析器获得。

#### 固定滑窗问题

- 在句子、表格或语义单元中间切断，导致 Chunk 不完整。
- 标题与正文分离，片段失去上下文。
- Chunk 太小导致语义不足，Chunk 太大又会降低检索精度并增加 Token 成本。
- Overlap 太小容易断语义，太大则产生重复召回、索引膨胀和上下文冗余。
- 只按字符或 Token 切分，无法表达章节、段落、表格等结构。

### 3. 改进方案

#### 先判断 PDF 类型

- **文本型 PDF**：优先使用能保留布局坐标和字体信息的解析器。
- **扫描型 PDF**：使用 PaddleOCR、其他 OCR 或视觉语言模型进行识别。
- **复杂表格 PDF**：使用 Camelot、Tabula 等表格工具；无文本层时应先 OCR。
- **图文混排 PDF**：结合布局分析、OCR、表格解析和图片理解。

&gt; Camelot 主要用于文本型 PDF 的表格提取，本身不是通用 OCR 工具。

#### 使用结构感知解析

- 识别标题、段落、列表、表格、图片、页眉和页脚。
- 根据字体大小、位置和编号恢复章节层级。
- 删除重复的页眉、页脚、目录和水印等噪声。
- 将中间结果统一为 Markdown 或带结构的 JSON，保留标题层级、页码、元素类型与坐标。

#### 使用语义切分

- 优先按“章节 → 小节 → 段落 → 句子”切分，固定 Token 滑窗只作为兜底。
- 每个 Chunk 附带文档名、章节路径、页码、时间、权限等元数据。
- 标题可以拼接到其下属 Chunk 中，避免正文失去主题。
- 表格尽量保持整体，过大的表格按表头重复、行组切分。
- 对长段落采用递归切分，并设置适量 Overlap。
- 可采用 Parent-Child Retrieval：小块负责精确召回，大块负责给 LLM 提供完整上下文。

#### 解析质量校验

- 统计空页、乱码率、文本长度异常、表格数量和 OCR 置信度。
- 抽样比较 PDF 原页与解析结果。
- 为解析器和切分策略建立带标注的回归测试集。
- 保存原页码和坐标，便于答案引用、问题回溯和可视化高亮。

### 4. 一个较完整的口述答案

&gt; PDF 不是天然的语义文档，而是页面绘制格式，所以固定滑窗前最大的问题通常出在解析：多栏顺序错乱、页眉页脚污染、表格行列丢失、扫描件无文本层，以及标题和正文关系丢失。固定滑窗还可能从句子或表格中间切断，并造成 overlap 重复。我会先区分文本型、扫描型和复杂表格型 PDF，分别使用布局解析、OCR 和表格工具；中间结果转成保留标题层级、页码和元素类型的 Markdown 或 JSON；再按章节、段落和语义单元切分，固定长度作为兜底。同时保存元数据，并用抽样检查和解析回归集评估质量。

## 三、RAG 出现 bad case，如何快速定位并修复？

### 1. 先建立可观测性

每次请求都应记录统一 Trace ID，并保存或采样记录以下信息：

- 原始问题、标准化问题、意图识别和 Query Rewrite 结果。
- 实际检索的知识库、租户和权限过滤条件。
- 召回文档 ID、Chunk 内容、召回分数与使用的检索参数。
- 重排前后顺序、重排分数和阈值。
- 最终送给 LLM 的上下文与 Prompt 模板版本。
- 模型版本、生成参数、答案和引用。
- 各阶段耗时、异常、超时、缓存命中情况。

要注意日志脱敏、访问控制和数据保留周期，不能为了排障泄露敏感信息。

### 2. 用“黄金证据漏斗”定位

先由人工或标注数据确定：正确答案是什么，以及支持答案的 Gold Chunk/Gold Document 是什么。然后依次检查：

```text
知识源中有正确内容吗？
  └─ 否：数据源问题
  └─ 是：解析后的内容正确吗？
       └─ 否：解析/OCR/切分问题
       └─ 是：Gold Chunk 已进入索引吗？
            └─ 否：摄取/索引更新问题
            └─ 是：初次召回命中了吗？
                 └─ 否：查询理解/Embedding/检索/过滤问题
                 └─ 是：重排后还保留吗？
                      └─ 否：重排问题
                      └─ 是：最终 Prompt 中存在吗？
                           └─ 否：去重/截断/上下文组装问题
                           └─ 是：模型仍答错？
                                └─ Prompt/生成/模型能力问题
```

### 3. 各阶段典型问题与修复

| 阶段 | 常见现象 | 可能原因 | 常用修复 |
| --- | --- | --- | --- |
| 数据源 | 根本找不到答案 | 知识缺失、内容过期、版本错误 | 补充数据、版本管理、增量更新 |
| 解析 | 原文有答案，解析结果没有 | OCR、表格、版面、乱码问题 | 更换解析器、结构化解析、人工规则 |
| 切分 | 答案被分散在多个 Chunk | Chunk 太小、标题分离、边界不合理 | 语义切分、增加适量 overlap、Parent-Child |
| 索引 | Chunk 已生成但检索不到 | 索引未更新、Embedding 版本不一致 | 重建或增量更新索引、版本校验 |
| 查询理解 | 用户表达与文档说法差异大 | 缩写、歧义、指代、多轮上下文缺失 | Query Rewrite、同义词、实体识别、多查询 |
| 召回 | Gold Chunk 未进入 top-k | 向量模型不匹配、k 太小、过滤错误 | 混合检索、调参、增大候选、修复过滤 |
| 重排 | Gold Chunk 被排到后面 | Reranker 领域不匹配、候选被截断 | 更换/微调模型、调整候选数与阈值 |
| 上下文组装 | 检索正确但 Prompt 中没有 | Token 截断、去重错误、排序错误 | 预算分配、上下文压缩、调整排序 |
| 生成 | 证据充分但模型答错 | 指令不清、幻觉、推理能力不足 | 强化引用约束、改 Prompt、模型路由 |
| 权限 | 结果异常少或发生越权 | Metadata Filter 错误 | 校验 ACL、租户隔离和缓存键 |

### 4. 快速止血与长期修复

#### 快速止血

- 补充或修正高频问题的知识内容。
- 调整 `top_k`、过滤条件、重排阈值或上下文 Token 预算。
- 对确定性高的高频问题增加缓存或结构化问答。
- 要求模型“只根据证据作答，证据不足时明确拒答”。
- 对高风险场景增加置信度门控、人工兜底或暂时降级。

#### 长期修复

- 将 bad case 加入离线评测集和回归测试集。
- 给失败原因打标签，统计各类型占比与趋势。
- 分阶段建立指标，避免只能看到最终答案好坏。
- 对解析器、Embedding、Reranker、Prompt 和模型进行版本化管理。
- 上线前进行离线回放，上线后进行灰度、A/B 测试和持续监控。

### 5. 一个较完整的口述答案

&gt; 我会先确保链路可观测，每次请求记录 Query Rewrite、过滤条件、召回和重排结果、最终上下文、Prompt、模型版本与各阶段耗时。定位时使用 Gold Chunk 漏斗：先确认数据源是否有答案，再确认解析和切分是否正确、索引是否包含它、初次召回是否命中、重排是否保留、最终 Prompt 是否包含。如果证据已经进入 Prompt 但模型仍答错，才重点检查 Prompt 和生成模型。修复后不能只改线上参数，还要把这个 bad case 加入回归集，防止后续版本再次出现。

## 四、如何评价 RAG 系统的好坏？

### 1. 总体框架

RAG 不能只看最终回答是否“像对的”，应分四层评估：

1. **检索层**：正确证据能不能被找到、排得是否足够靠前。
2. **生成层**：答案是否正确、忠实于证据、与问题相关。
3. **业务层**：是否真正帮助用户完成任务。
4. **工程层**：延迟、吞吐量、成本、稳定性和安全性是否达标。

### 2. 检索指标

设某个问题的相关文档集合为 `G`，系统返回的前 `K` 个结果为 `R_K`。

#### Hit Rate@K

前 K 个结果中是否至少存在一个相关文档：

```text
Hit@K = 1，若 R_K 中至少有一个相关文档；否则为 0
```

适合每个问题只需要命中一个关键证据的场景。

#### Recall@K

```text
Recall@K = |G ∩ R_K| / |G|
```

衡量所有相关文档中有多少被召回。若每个问题只有一个 Gold Chunk，Recall@K 与 Hit@K 在单样本上等价。

#### Precision@K

```text
Precision@K = |G ∩ R_K| / K
```

衡量召回结果中的相关内容占比，可以反映上下文噪声。

#### MRR

```text
MRR = mean(1 / rank_of_first_relevant_result)
```

越早出现第一个正确结果，得分越高。

#### nDCG@K

适合相关性有等级、且关心排序质量的场景；高相关结果排在前面时得分更高。

&gt; 实际评估通常同时看 Recall@K 和 MRR/nDCG：前者看“找没找到”，后者看“排得好不好”。

### 3. 生成指标

- **Answer Correctness**：答案与参考答案在事实和语义上是否一致。
- **Faithfulness/Groundedness**：答案中的陈述能否由检索上下文支持，是否存在幻觉。
- **Answer Relevance**：答案是否直接回应了用户问题。
- **Context Precision**：送入模型的上下文中，有用信息的比例。
- **Context Recall**：回答问题所需的证据是否被上下文覆盖。
- **Citation Correctness**：引用是否真的支持对应陈述。
- **拒答准确性**：知识不足时是否能正确拒答，而不是编造。

可以使用 RAGAS、TruLens 或自建 LLM-as-a-Judge 流程进行自动化评估。

#### LLM-as-a-Judge 的注意点

- Judge Prompt、评分标准和模型版本必须固定并版本化。
- 对调换答案顺序、模型偏好、长度偏好等偏差进行测试。
- 使用人工标注集校准自动评分，并持续检查相关性。
- 高风险任务不能完全依赖单个 Judge 模型。

### 4. 业务和端到端指标

- 用户任务完成率、问题解决率。
- 人工审核正确率、专家通过率。
- 用户满意度 CSAT、点赞率、投诉率。
- 转人工率、重复提问率、会话解决时长。
- 不同业务场景下的转化率或效率提升。
- 线上 A/B 测试结果。

自动指标最终应和业务指标建立关联，否则可能出现“离线分数上涨，用户体验没有变好”。

### 5. 工程指标

- 端到端 P50、P95、P99 延迟，以及 TTFT、TPOT。
- QPS、并发能力和 Token 吞吐量。
- 单次请求成本、Embedding/重排/生成 Token 成本。
- CPU、GPU、内存和向量库资源占用。
- 可用性、超时率、错误率、降级率。
- 缓存命中率、索引更新时延、知识新鲜度。
- 权限泄露率、敏感信息暴露等安全指标。

### 6. 如何建设评测集

- 从真实用户日志中抽样，覆盖高频问题、长尾问题和历史 bad case。
- 加入多跳问题、歧义问题、口语化问题、错别字、缩写和无答案问题。
- 为每个问题标注参考答案、Gold Document/Chunk、问题类型和难度。
- 按业务域、用户群、文档类型、语言等维度分层统计，避免平均分掩盖局部退化。
- 严格区分开发集、验证集和测试集，防止针对测试集过拟合。
- 评测集随线上问题持续更新，但要保留稳定基准集用于版本横向比较。

### 7. 一个较完整的口述答案

&gt; 我会从检索、生成、业务和工程四层评估 RAG。检索层看 Recall@K、Hit Rate@K、MRR 和 nDCG，分别衡量正确证据是否被召回以及排序是否靠前；生成层看答案正确性、忠实度、相关性、上下文精确率和召回率，可以用 RAGAS、TruLens 或 LLM-as-a-Judge，但需要用人工标注校准；业务层看任务完成率、人工通过率、CSAT 和 A/B 测试；工程层看 P95/P99 延迟、QPS、成本、错误率和知识新鲜度。评测集要来自真实流量，并覆盖普通问题、长尾问题、无答案问题和历史 bad case。

## 五、面试中的通用回答框架

### 1. 回答系统优化题

使用以下顺序：

1. 先给出全链路拆解。
2. 说明先测量、再优化，不凭感觉换模型。
3. 分阶段给出两到三个核心方案。
4. 主动说明效果、延迟、成本之间的权衡。
5. 最后用离线评测和线上 A/B 验证。

### 2. 回答故障排查题

使用以下顺序：

1. 建立 Trace 和日志。
2. 准备正确答案和 Gold Chunk。
3. 沿链路逐层检查，寻找正确证据在哪一步丢失。
4. 先止血，再根治。
5. 将 bad case 加入回归集。

### 3. 回答评估题

不要只回答“准确率”，而要覆盖：

```text
检索效果 &#43; 生成质量 &#43; 业务价值 &#43; 工程质量
```

并主动补充评测集构建、人工校准、线上 A/B 和持续监控。

### 4. 面试加分点

- 能区分 Recall@K、Hit Rate@K、MRR 和 nDCG 的适用场景。
- 能说明 Streaming 降低的是感知延迟，不一定降低总耗时。
- 能说明 PDF 是页面布局格式，不能简单等同于结构化文本。
- 能用 Gold Chunk 漏斗定位 bad case，而不是一律归因于大模型。
- 能同时讨论效果、延迟、成本、安全和知识新鲜度。
- 能说明任何线上修复都应进入评测集和回归流程。

## 六、30 秒总复习

```text
性能优化：先拆链路和测 P95，再优化 Embedding、召回、重排、LLM 与架构。

PDF 处理：先做结构化解析，再按语义切分；OCR、表格和版面需要分别处理。

Bad Case：准备 Gold Chunk，沿“数据→解析→索引→召回→重排→Prompt→生成”逐层定位。

系统评估：检索看 Recall/MRR，生成看正确性和忠实度，线上看业务指标，工程看延迟成本与稳定性。
```
